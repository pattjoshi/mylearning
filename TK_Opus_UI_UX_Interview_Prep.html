1. HTML5 & Semantic Markup (Q1–Q20)

Q1. What is HTML5 and how is it different from older HTML versions?
Answer: HTML5 is the latest version of HTML. The big differences are:
• New semantic tags like <header>, <footer>, <article>, <section>, <nav> — these give meaning to your page structure instead of using <div> everywhere.
• Native multimedia — <video> and <audio> tags let you play media without Flash.
• Canvas & SVG — draw graphics directly in the browser.
• Form improvements — new input types like email, date, range, and validation attributes.
• APIs — localStorage, geolocation, drag-and-drop, web workers, etc.
• Mobile-friendly — better support for touch and responsive design.
Q2. Why should you use semantic HTML tags instead of <div> everywhere?
Answer: Semantic tags (like <header>, <nav>, <main>, <article>, <section>, <aside>, <footer>) tell browsers, screen readers, and search engines what each part of the page means. Benefits:
• Accessibility — screen readers can navigate the page properly.
• SEO — search engines understand your content better and rank it higher.
• Readability — developers can understand the page structure at a glance.
• Future-proof — standards-aligned code works across all modern browsers.
Q3. What is the difference between <div> and <section>?
Answer: A <div> is a generic container with no meaning. Use it when you need a wrapper for styling or JavaScript but the content has no special meaning. A <section> is a thematic group of content that should have a heading. Use it when the content logically forms a section (e.g., "Latest Products", "Customer Reviews"). Rule: if the content makes sense with a heading, use <section>; otherwise use <div>.
Q4. What is the <meta viewport> tag and why is it important?
Answer: The viewport meta tag tells the browser how to control the page's dimensions and scaling on mobile devices.
Code: <meta name="viewport" content="width=device-width, initial-scale=1.0">
• width=device-width — makes the page width match the device screen width.
• initial-scale=1.0 — sets the starting zoom level to 100%.
Without this tag, mobile browsers may show a zoomed-out desktop view, making your site hard to read and use on phones.
Q5. Explain the <picture> element and its use case.
Answer: The <picture> element lets you serve different image files based on screen size, device type, or image format support. This improves performance and visual quality.
Example: 
<picture>
  <source media="(min-width: 1024px)" srcset="hero-desktop.webp" type="image/webp">
  <source media="(min-width: 768px)" srcset="hero-tablet.webp" type="image/webp">
  <source srcset="hero-mobile.webp" type="image/webp">
  <img src="hero-mobile.jpg" alt="Hero banner">
</picture>
The browser picks the best source. The <img> tag at the end is the fallback if none of the sources match or if the browser doesn't support <picture>.
Q6. What is the difference between localStorage, sessionStorage, and cookies?
Answer: All three store data in the browser but differ in:
• localStorage — persists even after closing the browser. No expiry. Max ~5–10MB. Not sent to the server. Best for user preferences, cached data.
• sessionStorage — data is cleared when the tab is closed. Same size limit. Best for temporary session data.
• Cookies — sent to the server with every HTTP request. Small size (4KB). Can set expiry. Used for authentication, tracking, server-side session management.
Q7. What are data-* attributes in HTML5?
Answer: data-* attributes let you store extra information inside HTML elements without using non-standard attributes or extra classes. They are accessed via JavaScript using element.dataset.
Example: <button data-user-id="123" data-role="admin">Edit</button>
In JS: button.dataset.userId → "123", button.dataset.role → "admin".
Use them for storing simple data that you need in your JavaScript logic (not for sensitive data — it's visible in HTML).
Q8. What is the difference between <em> and <i>? Between <strong> and <b>?
Answer: <em> (emphasis) has meaning — it indicates stressed emphasis in the content. Screen readers change their tone when reading it. <i> is visual only — used for italics without meaning (e.g., a foreign word, a technical term).
Similarly, <strong> has meaning — it indicates strong importance. Screen readers emphasize it. <b> is visual only — used for bold styling without added meaning.
Rule: use semantic tags (<em>, <strong>) for meaning; use <i>, <b> for purely visual styling.
Q9. Explain the HTML5 form input types. Give examples.
Answer: HTML5 introduced many input types for better user experience and built-in validation:
• text — single-line text (default)
• email — validates email format; shows email keyboard on mobile
• url — validates URL format
• number — only numbers; shows number pad on mobile
• tel — shows phone keypad on mobile
• date, time, datetime-local — date/time pickers
• color — color picker
• range — slider control
• search — search field with clear button
• file — file upload
• password — masked input
• checkbox, radio — selection controls
• submit, reset, button — buttons
Q10. What is the purpose of the <figure> and <figcaption> elements?
Answer: <figure> is a semantic container for self-contained content like images, diagrams, illustrations, or code snippets. <figcaption> provides the caption for that content. The figure and its caption are treated as one unit.
Example: 
<figure>
  <img src="dashboard-chart.png" alt="Monthly sales chart">
  <figcaption>Sales performance for Q1 2026</figcaption>
</figure>
You could wrap multiple images inside one figure if they share one caption.
Q11. What is the difference between <article> and <section>?
Answer: <article> is for independent, self-contained content that could be distributed separately (blog post, news story, forum post, product card). <section> is for thematic grouping within a page (e.g., "Features" section, "Pricing" section). An article can contain multiple sections. A section can contain multiple articles. Both should have a heading.
Q12. How does the HTML5 <audio> element work?
Answer: The <audio> element lets you embed sound without plugins like Flash.
Example: 
<audio controls>
  <source src="music.mp3" type="audio/mpeg">
  <source src="music.ogg" type="audio/ogg">
  Your browser does not support the audio element.
</audio>
Attributes: controls (show play/pause), autoplay, loop, muted, preload. Provide multiple source tags for browser compatibility. The text between tags is the fallback message.
Q13. What is the <template> tag?
Answer: The <template> tag holds HTML that is not rendered immediately but can be cloned and inserted later with JavaScript. The content is hidden, not loaded, and doesn't affect performance. It's ideal for creating reusable HTML chunks.
Example: 
<template id="card-template">
  <div class="card">
    <h3 class="card-title"></h3>
    <p class="card-desc"></p>
  </div>
</template>

<script>
  const template = document.getElementById('card-template');
  const clone = template.content.cloneNode(true);
  clone.querySelector('.card-title').textContent = 'My Card';
  document.body.appendChild(clone);
</script>
Q14. What is progressive enhancement?
Answer: Progressive enhancement is a design strategy where you build the core content and basic functionality first (works for everyone, every browser), then add advanced features and styling layer by layer for browsers that support them. Example: a form that works with plain HTML, then gets JavaScript validation, then gets fancy animations — users with JavaScript disabled still can submit the form. The opposite approach (graceful degradation) builds the full experience first and tries to make it work in older browsers.
Q15. What is the difference between <canvas> and SVG?
Answer: Both draw graphics but work differently:
• Canvas — pixel-based (raster). You draw with JavaScript commands on a grid. Once drawn, individual shapes cannot be modified — you redraw the whole canvas. Better for: games, image processing, real-time animation, many objects (e.g., 5000+ particles).
• SVG — shape-based (vector). XML tags define shapes. Each shape is a DOM element you can style with CSS, attach events to, and modify individually. Better for: logos, icons, charts, interactive diagrams, responsive graphics that need to scale to any size.
Q16. Explain the HTML5 drag-and-drop API.
Answer: HTML5 supports native drag-and-drop. Key events: dragstart, drag, dragenter, dragover, dragleave, drop, dragend. Make an element draggable with draggable="true".
Example: 
<div draggable="true" id="item" ondragstart="event.dataTransfer.setData('text/plain', 'Item')">Drag me</div>
<div ondrop="event.preventDefault(); alert('Dropped!');" ondragover="event.preventDefault();">Drop here</div>
Call preventDefault() on dragover to allow a drop. Use dataTransfer object to pass data between drag and drop.
Q17. What is the role of the <head> section in an HTML document?
Answer: The <head> contains metadata about the page — data that is not displayed as content. This includes:
• <title> — page title shown in the browser tab and search results.
• <meta> — character set, viewport, description, keywords, Open Graph tags for social sharing.
• <link> — links to CSS files, favicon, preload/prefetch resources.
• <script> — JavaScript (ideally placed at the end of body, not in head).
• <style> — internal CSS (rarely used in production; external CSS is preferred).
A well-structured <head> improves SEO, accessibility, and performance.
Q18. What are Web Workers?
Answer: Web Workers let you run JavaScript in the background thread without blocking the UI. JavaScript is normally single-threaded — heavy calculations freeze the page. A worker runs a separate script in a separate thread.
Example: 
// main.js
const worker = new Worker('worker.js');
worker.postMessage('Start calculation');
worker.onmessage = function(e) { console.log('Result:', e.data); };

// worker.js
onmessage = function(e) {
  let result = 0;
  for (let i = 0; i < 1000000000; i++) result += i;
  postMessage(result);
};
Workers cannot access the DOM, window, or parent object — they communicate via messages.
Q19. How do you embed a favicon in HTML?
Answer: Place the favicon file (.ico, .png, or .svg) in your project root and link it in the <head>:
<link rel="icon" type="image/x-icon" href="/favicon.ico">
For modern formats:
<link rel="icon" type="image/svg+xml" href="/favicon.svg">
For Apple devices:
<link rel="apple-touch-icon" href="/apple-touch-icon.png">
Browsers automatically request /favicon.ico from the root, but explicit linking is more reliable and supports different sizes.
Q20. What is the difference between <script>, <script async>, and <script defer>?
Answer: • <script> (without attributes) — HTML parsing pauses when the script is encountered, downloads and executes the script, then resumes parsing. Slows down page load.
• <script async> — downloads in parallel while HTML parses, but executes immediately when downloaded — pausing parsing. Order is not guaranteed (useful for independent scripts like analytics).
• <script defer> — downloads in parallel while HTML parses, but waits to execute until the HTML is fully parsed. Scripts execute in order. Best for scripts that need the full DOM (most use cases).
Tip: use <script defer> in the <head> for your main scripts — it loads early and runs after the page is ready.

2. CSS3 & Responsive Design (Q21–Q45)

Q21. What is the CSS Box Model?
Answer: The box model describes how every HTML element is structured as a box with four layers (from inside to outside):
1. Content — the actual content (text, image).
2. Padding — space between content and border. Transparent. Adds to element size.
3. Border — border around padding.
4. Margin — space outside the border. Transparent. Separates elements from each other.
Important: With box-sizing: content-box (default), width/height only includes content. With box-sizing: border-box, width/height includes content + padding + border — this is the standard modern practice to make sizing more intuitive.
Q22. What is Flexbox?
Answer: Flexbox (CSS Flexible Box Layout) is a one-dimensional layout model that distributes space and aligns items in a row or column. It's great for navigation bars, centering, card rows, and any layout where items need to distribute space flexibly. Key properties:
• Parent (flex container): display: flex, flex-direction, justify-content (main axis), align-items (cross axis), flex-wrap, gap.
• Children (flex items): flex (shorthand for flex-grow, flex-shrink, flex-basis), align-self, order.
Example — centering a div: display: flex; justify-content: center; align-items: center; height: 100vh;
Q23. What is CSS Grid?
Answer: CSS Grid is a two-dimensional layout system that works on rows and columns simultaneously. Grid is best for complex page layouts, dashboards, image galleries, and any design that needs both row and column control. Key properties:
• Container: display: grid, grid-template-columns, grid-template-rows, gap, grid-template-areas.
• Items: grid-column, grid-row, grid-area.
Example — 3-column layout: display: grid; grid-template-columns: repeat(3, 1fr); gap: 20px;
Q24. Flexbox vs Grid — when to use which?
Answer: Use Flexbox when you need one-dimensional layout — either a row OR a column. Examples: navbar, centering, button groups, card rows that wrap to next line. Use Grid when you need two-dimensional layout — both rows AND columns. Examples: page layouts, dashboard grids, image galleries, calendars. You can also use them together — use Grid for the overall page layout, then Flexbox inside individual components.
Q25. What are media queries?
Answer: Media queries apply CSS rules based on conditions like screen width, device type, or orientation. They are the foundation of responsive design.
Example: 
/* Default: mobile styles */
.container { display: flex; flex-direction: column; }

/* Tablet and above */
@media (min-width: 768px) {
  .container { flex-direction: row; }
}

/* Desktop */
@media (min-width: 1024px) {
  .container { max-width: 960px; margin: 0 auto; }
}
Common breakpoints: 480px (mobile), 768px (tablet), 1024px (desktop), 1440px (wide).
Q26. What is the difference between em, rem, px, and % in CSS?
Answer: • px — absolute, fixed size. Good for borders, shadows, small details. Not ideal for text because it doesn't scale with user's browser settings.
• em — relative to the parent element's font-size. Can cascade and compound (e.g., nested elements multiply). Good for padding/margin relative to font size.
• rem — relative to the root (html) font-size (usually 16px). Does not compound. Best for font sizes — easy to maintain and accessible.
• % — relative to the parent element's same property. Good for widths, heights, and responsive layouts.
Modern practice: use rem for font sizes, % for widths, em for padding/margin on buttons, px for tiny details (borders, shadows).
Q27. What are CSS Custom Properties (CSS Variables)?
Answer: CSS variables store reusable values that you can change dynamically. They are defined with -- prefix and accessed with var(). They support theming and are accessible in JavaScript.
Example: 
:root {
  --primary-color: #2563eb;
  --border-radius: 8px;
  --spacing-md: 16px;
}
.button {
  background: var(--primary-color);
  border-radius: var(--border-radius);
  padding: var(--spacing-md);
}
You can change variables with media queries or JavaScript to create themes. This is much more maintainable than hardcoding values everywhere.
Q28. What is the difference between position: relative, absolute, fixed, and sticky?
Answer: • relative — element stays in normal document flow, but you can offset it with top/left/right/bottom. The original space is preserved.
• absolute — element is removed from normal flow. Positioned relative to the nearest positioned ancestor (or the initial containing block). Does not reserve space. Use for overlays, tooltips, dropdowns.
• fixed — element is removed from normal flow. Positioned relative to the viewport. Stays in place when scrolling. Good for sticky headers, back-to-top buttons.
• sticky — hybrid of relative and fixed. Behaves like relative until a scroll threshold is reached, then "sticks" to the viewport. Great for section headers that stay visible while scrolling through content.
Q29. What is a pseudo-class? Give examples.
Answer: A pseudo-class is a keyword added to a selector that styles an element based on its state or position. It starts with a single colon (:).
Common examples:
• :hover — mouse over element
• :focus — element has keyboard focus
• :active — element is being clicked
• :nth-child(n) — nth child element
• :first-child, :last-child
• :not(selector) — excludes matching elements
• :disabled, :checked — form element states
• :focus-visible — focus only when using keyboard (great for accessibility)
Q30. What is a pseudo-element? Give examples.
Answer: A pseudo-element styles a specific part of an element or inserts content before/after it. It uses double colon (::).
Common examples:
• ::before — inserts content before element's content
• ::after — inserts content after element's content
• ::first-letter — first letter of text
• ::first-line — first line of text
• ::placeholder — placeholder text in inputs
• ::selection — text selected by user
Important: ::before and ::after need content: '' to work. They are widely used for icons, custom checkboxes, decorative elements, and tooltips.
Q31. Explain the concept of "mobile-first" CSS.
Answer: Mobile-first means you write the base CSS for small screens first, then use min-width media queries to add more styles for larger screens. This ensures the core experience works on all devices. Reason: it's easier to add complexity for larger screens than to try and strip it away for mobile. The default CSS is the mobile version; everything else is progressive enhancement. Example: a single-column layout by default becomes multi-column at larger breakpoints.
Q32. What is the CSS display property?
Answer: The display property controls how an element is rendered. Common values:
• block — takes full width, starts on new line (div, p, h1)
• inline — fits within text, no width/height control (span, a, strong)
• inline-block — inline but can have width/height and padding
• none — element completely removed from layout (not rendered)
• flex — flexbox container
• grid — grid container
• table, table-cell — table-like layout
Q33. What is the CSS visibility: hidden vs display: none?
Answer: display: none completely removes the element from the document flow — it takes no space and is not rendered. visibility: hidden makes the element invisible but it still takes space in the layout. Use display: none when you want to hide completely (like a conditional section); use visibility: hidden when you need to hide content without shifting layout (like a loading state that becomes visible later).
Q34. What are CSS transitions?
Answer: CSS transitions smoothly animate changes from one property value to another when a state change (like hover) occurs.
Example: 
.button {
  background: blue;
  transition: background 0.3s ease;
}
.button:hover { background: darkblue; }
Properties: transition-property, transition-duration, transition-timing-function (ease, linear, ease-in-out), transition-delay. Shorthand: transition: all 0.3s ease. For performance, prefer transitioning opacity and transform over width/height/top/left (they trigger expensive layout recalculations).
Q35. What are CSS animations and @keyframes?
Answer: CSS animations let you create more complex, multi-step animations using @keyframes. They don't require user interaction (can run on page load).
Example: 
@keyframes fadeIn {
  from { opacity: 0; transform: translateY(20px); }
  to   { opacity: 1; transform: translateY(0); }
}
.element {
  animation: fadeIn 0.5s ease forwards;
}
Key properties: animation-name, animation-duration, animation-timing-function, animation-delay, animation-iteration-count (infinite, number), animation-direction (normal, reverse, alternate).
Q36. What is the z-index property?
Answer: z-index controls the stacking order of overlapping elements along the Z axis (front to back). Higher z-index values appear in front. It only works on positioned elements (position: relative/absolute/fixed/sticky) or flex/grid items. Important concepts:
• Stacking context — each positioned element with a z-index creates its own stacking context. z-index values only compare within the same context.
• Values can be any integer. Default is auto (0).
• Common issues: nested elements with z-index behave unexpectedly because of stacking contexts.
Q37. What is the :root selector?
Answer: :root is a pseudo-class that selects the document's root element — which is always the <html> element in HTML, but with higher specificity. It's commonly used to define global CSS variables.
Code: 
:root {
  --primary: #2563eb;
  --text-color: #1a1a1a;
  --bg-color: #ffffff;
}
Q38. Explain the CSS calc() function.
Answer: calc() lets you perform mathematical calculations in CSS values, mixing different units. This is powerful for responsive layouts where you need to subtract fixed values from percentages.
Examples:
width: calc(100% - 40px); — full width minus padding
height: calc(100vh - 60px - 2rem); — viewport height minus header and spacing
grid-template-columns: calc(25% - 10px) 1fr; — mixed units in grid
Supported operators: +, -, *, /. Always put spaces around + and -.
Q39. What is the object-fit property?
Answer: object-fit controls how an image or video fits within its container (preserving or not preserving aspect ratio). Values:
• fill (default) — stretches to fill, may distort aspect ratio
• contain — fits entirely within container, preserves ratio, may leave empty space
• cover — fills container completely, may crop parts of the image (most common for hero images and thumbnails)
• none — original size, may overflow
• scale-down — smallest version between none and contain
Use object-position to set which part of the image stays visible when using cover.
Q40. What is the clamp() function?
Answer: clamp() is a CSS function that clamps a value between a minimum and maximum — it's the ultimate responsive sizing tool. Syntax: clamp(minimum, preferred, maximum).
Example: font-size: clamp(1rem, 2.5vw, 2rem);
This sets font-size to 2.5vw but never smaller than 1rem and never larger than 2rem. The font scales fluidly between these bounds. This eliminates the need for multiple media queries just for font sizes.
Q41. What are CSS combinators?
Answer: Combinators define relationships between selectors:
• Descendant (space) — div p selects all p inside div (any depth)
• Child (>) — div > p selects only direct children (one level deep)
• Adjacent sibling (+) — h2 + p selects the first p immediately after h2
• General sibling (~) — h2 ~ p selects all p siblings after h2
Q42. What is specificity in CSS?
Answer: Specificity determines which CSS rule applies when multiple rules target the same element. The browser calculates a score: inline styles (1000) > IDs (100) > classes, attributes, pseudo-classes (10) > elements, pseudo-elements (1). The rule with the highest specificity wins. If equal, the last one in the stylesheet wins. Best practice: keep specificity low — use classes instead of IDs for styling, avoid !important (it overrides everything). Low specificity makes CSS easier to maintain and override.
Q43. What is the !important rule and why avoid it?
Answer: !important overrides ANY other CSS rule regardless of specificity. It's a last resort that makes future changes very difficult — you need !important to override !important. Avoid it by writing well-structured, appropriately specific selectors. Only use !important for: utility/helper classes (like .hidden), user preference overrides (like accessibility), or when you can't change third-party CSS.
Q44. What does the transform property do?
Answer: transform modifies the position, size, and rotation of an element without affecting the layout of surrounding elements. Common functions: translate() (move), rotate(), scale(), skew(). Multiple transforms can be combined: transform: translateX(50px) rotate(45deg) scale(1.2). Transforms are GPU-accelerated, making them efficient for animations.
Q45. What are CSS Reset and Normalize.css?
Answer: Browsers have different default styles. A CSS Reset strips all default styling (margins, paddings, font sizes) to zero, giving you a completely blank slate (e.g., Eric Meyer's Reset). Normalize.css keeps useful defaults but makes them consistent across browsers — it normalizes differences rather than removing everything. Most modern projects use Normalize.css or a utility-first framework like Tailwind that includes its own normalization. Alternatively, you can set * { box-sizing: border-box; margin: 0; padding: 0; } as a simple starting point.

3. JavaScript Core & ES6+ (Q46–Q80)

Q46. What is the difference between let, const, and var?
Answer: • var — function-scoped. Can be redeclared and updated. Hoisted to the top of its function. Avoid in modern JavaScript.
• let — block-scoped (inside { }). Can be updated but not redeclared in the same scope. Use for variables that will change.
• const — block-scoped. Cannot be updated or redeclared. Must be initialized when declared. Use by default — only use let when you know the value will change. Note: const objects/arrays can have their properties mutated — the binding is constant, not the value.
Q47. What is the difference between == and ===?
Answer: == compares values after type coercion (converts types automatically). Example: 5 == "5" is true. === compares values without type coercion — both value and type must match. Example: 5 === "5" is false. Always use === to avoid unexpected bugs from type coercion. The only exception is when you explicitly need to check null/undefined: value == null checks both null and undefined.
Q48. What are arrow functions? How are they different from regular functions?
Answer: Arrow functions (() => {}) are a shorter syntax for writing functions. Key differences:
• No own this — arrow functions inherit this from the surrounding scope (lexical this). Regular functions have their own this based on how they're called.
• Cannot be used as constructors — arrow functions don't have prototype and can't be used with new.
• No arguments object — use rest parameters (...args) instead.
• Implicit return for single-expression bodies: const double = x => x * 2.
Use arrow functions for callbacks, array methods, and when you want to preserve this context. Use regular functions for methods that need their own this binding or constructor functions.
Q49. What is a Promise?
Answer: A Promise is an object representing the eventual completion (or failure) of an asynchronous operation. It has three states: pending (initial state), fulfilled (success — .then() runs), rejected (error — .catch() runs).
Example: 
const fetchData = new Promise((resolve, reject) => {
  setTimeout(() => resolve("Data loaded"), 1000);
});
fetchData
  .then(data => console.log(data))
  .catch(error => console.error(error))
  .finally(() => console.log("Done"));
Promises make async code cleaner than callbacks and prevent "callback hell."
Q50. What is async/await?
Answer: async/await is syntactic sugar over Promises that makes asynchronous code read like synchronous code. async marks a function as asynchronous (always returns a Promise). await pauses execution until a Promise resolves.
Example: 
async function getUserData(userId) {
  try {
    const response = await fetch(`/api/users/${userId}`);
    const data = await response.json();
    return data;
  } catch (error) {
    console.error("Failed to fetch user:", error);
    throw error;
  }
}
Always use try/catch with await to handle errors properly.
Q51. What is the event loop in JavaScript?
Answer: JavaScript is single-threaded — it can only do one thing at a time. The event loop is what allows JavaScript to handle asynchronous operations (like API calls, timers, user clicks) without blocking. How it works: 1) The call stack runs synchronous code. 2) Async operations (like setTimeout, fetch) are handed to the browser APIs. 3) When they complete, their callbacks go to the task queue (macrotasks) or microtask queue. 4) The event loop constantly checks: when the call stack is empty, it first processes all microtasks (Promise callbacks), then one macrotask. This cycle repeats forever. Understanding the event loop helps avoid bugs with setTimeout and Promise ordering.
Q52. What are closures in JavaScript?
Answer: A closure is created when a function "remembers" the variables from its outer scope even after the outer function has finished executing. Example: 
function counter() {
  let count = 0;  // this variable is "closed over"
  return function() {
    count++;
    return count;
  };
}
const myCounter = counter();
console.log(myCounter()); // 1
console.log(myCounter()); // 2
Closures are used for: data privacy (encapsulation), creating factory functions, partial application, and maintaining state in callbacks. They are a fundamental concept in JavaScript that often comes up in interviews.
Q53. What is the this keyword? How does its value change?
Answer: this refers to the object that is executing the current function. Its value depends on how the function is called:
• Global context — this is window (browser) or global (Node).
• Regular function call — this is window (in strict mode: undefined).
• Method call (obj.method()) — this is the object.
• Event handler — this is the element that triggered the event.
• Arrow function — this is inherited from the outer (lexical) scope.
• .call(), .apply(), .bind() — you explicitly set this to whatever you pass.
Q54. What are template literals?
Answer: Template literals (template strings) use backticks (`) instead of quotes. They support: string interpolation with ${expression}, multi-line strings without \n, and tagged templates for advanced use.
Example: 
const name = "Alice";
const greeting = `Hello, ${name}!
Welcome to our platform.
You have ${3} new messages.`;
Q55. What is destructuring?
Answer: Destructuring is a shorthand to extract values from objects or arrays into individual variables.
Array destructuring: 
const [first, second, ...rest] = [1, 2, 3, 4, 5];
// first=1, second=2, rest=[3,4,5]
Object destructuring: 
const { name, age, address: { city } } = user;
// Extracts name, age, and nested city from user object
Also useful in function parameters: function ({ name, email }) { ... }.
Q56. What is the spread operator?
Answer: The spread operator (...) expands an array or object into individual elements. Used for:
• Copying: const copy = [...arr] or const obj = {...original} (shallow copy)
• Merging: const merged = [...arr1, ...arr2] or const obj = {...a, ...b}
• Passing to functions: Math.max(...numbers)
• Rest parameters: function sum(...args) { return args.reduce((a,b) => a+b, 0); }
Spread creates shallow copies — nested objects are still references to the original.
Q57. What is .map(), .filter(), and .reduce()?
Answer: These are array methods for functional programming:
• .map() — transforms every element. Returns a new array of the same length.
[1,2,3].map(x => x * 2) // [2,4,6]
• .filter() — keeps elements that pass a test. Returns a subset.
[1,2,3,4].filter(x => x > 2) // [3,4]
• .reduce() — accumulates values into a single result (any type).
[1,2,3].reduce((sum, x) => sum + x, 0) // 6
These are preferred over for-loops because they are declarative, chainable, and avoid side effects.
Q58. What is the difference between null and undefined?
Answer: undefined means a variable has been declared but not assigned a value (the default). null is an explicitly assigned value that represents "nothing" or "empty." typeof null returns "object" (this is a well-known JavaScript bug). typeof undefined returns "undefined". Use null when you want to intentionally indicate no value; undefined is the default uninitialized state.
Q59. What is hoisting?
Answer: Hoisting is JavaScript's default behavior of moving declarations to the top of their scope before code execution. Function declarations are fully hoisted (can be called before they appear in the code). var variables are hoisted but initialized as undefined — they return undefined before the assignment line. let and const are hoisted but not initialized — accessing them before declaration throws a ReferenceError (Temporal Dead Zone). Best practice: always declare variables at the top of their scope to avoid confusion.
Q60. What is the DOM?
Answer: DOM (Document Object Model) is a programming interface for HTML documents. The browser parses HTML into a tree of objects (nodes) that JavaScript can manipulate. You can change content, styles, structure, and handle events through the DOM API. Common operations: document.getElementById(), document.querySelector(), element.textContent, element.innerHTML, element.classList.add(), element.addEventListener().
Q61. What is event delegation?
Answer: Event delegation is a technique where you attach ONE event listener to a parent element instead of attaching listeners to each child. It works because events bubble up from the target element to the root. Benefits: better performance (fewer listeners), works for dynamically added elements.
Example: 
document.querySelector('ul').addEventListener('click', function(e) {
  if (e.target.tagName === 'LI') {
    console.log('Clicked:', e.target.textContent);
  }
});
Q62. What is the difference between localStorage and sessionStorage?
Answer: Both store data as key-value pairs in the browser. localStorage persists even after the browser is closed and reopened — no expiration. sessionStorage is cleared when the page session ends (tab is closed). Both have ~5-10MB storage limit (much larger than cookies). Both are synchronous and only store strings (use JSON.stringify/parse for objects). Data is not sent to the server automatically.
Q63. What is JSON? How do you convert between JSON and JavaScript objects?
Answer: JSON (JavaScript Object Notation) is a lightweight data-interchange format that's easy for humans to read and machines to parse. It looks like JavaScript objects but with double-quoted keys and string values. Convert JS object to JSON: JSON.stringify(obj). Convert JSON to JS object: JSON.parse(jsonString). JSON is used extensively in APIs and configuration files.
Q64. What is the difference between forEach and map?
Answer: Both iterate over arrays. forEach executes a callback on each element but does NOT return a new array — it's used for side effects (like modifying external variables, logging). map returns a new array with transformed values — it's used for data transformation and is chainable with other array methods. Use map when you need the result; use forEach when you just want to perform an action for each item.
Q65. What is the Fetch API?
Answer: The Fetch API provides a modern, Promise-based way to make HTTP requests in the browser. It replaces the older XMLHttpRequest.
Example: 
fetch('https://api.example.com/users', {
  method: 'GET',
  headers: { 'Content-Type': 'application/json' }
})
  .then(response => {
    if (!response.ok) throw new Error('HTTP error ' + response.status);
    return response.json();
  })
  .then(data => console.log(data))
  .catch(error => console.error(error));
Or with async/await: const data = await fetch(url).then(r => r.json()).
Q66. What are JavaScript data types?
Answer: JavaScript has 8 data types: Primitive types (immutable, stored by value) — string, number, bigint, boolean, undefined, null, symbol. Reference type (mutable, stored by reference) — object (includes arrays, functions, dates, etc.). Primitive comparison is by value; object comparison is by reference (two separately created objects are never === to each other).
Q67. What is the difference between deep copy and shallow copy?
Answer: A shallow copy copies only the top-level properties. Nested objects/arrays are still shared (referenced) between original and copy. Methods: spread operator (const copy = {...obj}), Object.assign(). A deep copy recursively copies all nested objects — no shared references. Methods: JSON.parse(JSON.stringify(obj)) (but loses functions, undefined, symbols), structuredClone() (modern browser API), or a library like Lodash (_.cloneDeep(obj)).
Q68. What are higher-order functions?
Answer: A higher-order function is a function that takes a function as an argument OR returns a function. Examples: Array.map(), Array.filter(), Array.reduce() — they all accept callback functions. setTimeout() and addEventListener() also take callbacks. Debounce and throttle utilities are created by functions returning functions. Higher-order functions enable functional programming patterns like composition and currying.
Q69. Explain the concept of "strict mode" in JavaScript.
Answer: Strict mode ("use strict";) opts into a restricted variant of JavaScript that catches common mistakes and prevents unsafe actions. Key effects: prevents accidental global variables (must declare with let/const/var), makes assignments that would silently fail throw errors, forbids deleting variables/functions, makes this undefined in regular functions (instead of window), and disables features like with. Always use strict mode in modern JavaScript — it's enabled by default in ES modules and classes.
Q70. What is the difference between synchronous and asynchronous code?
Answer: Synchronous code executes line by line — each operation blocks until it completes. If an operation takes 3 seconds, the entire page freezes for 3 seconds. Asynchronous code lets the program continue running while waiting for long operations (API calls, file reads, timers). In JavaScript, async operations use callbacks, Promises, or async/await. The event loop manages when async callbacks execute. Modern JavaScript heavily relies on async patterns for everything from API calls to user interactions.
Q71. What is the difference between function declaration and function expression?
Answer: Function declaration: function foo() {} — hoisted (can be called before definition), must have a name. Function expression: const foo = function() {} — NOT hoisted, can be anonymous or named. Arrow functions (const foo = () => {}) are also expressions. Function declarations are easier to read; function expressions give more control over when the function is defined.
Q72. What is the bind() method?
Answer: bind() creates a new function with a fixed this value (and optionally pre-filled arguments). Unlike call() and apply(), bind does NOT execute the function immediately — it returns a new function you call later.
Example: 
const user = { name: 'Alice' };
function greet(greeting) { return `${greeting}, ${this.name}`; }
const greetAlice = greet.bind(user, 'Hello');
console.log(greetAlice()); // "Hello, Alice"
Common uses: fixing this in event handlers, partial application (pre-filling arguments).
Q73. What is the call() and apply() method?
Answer: Both invoke a function with a specific this value. call() passes arguments individually: func.call(thisArg, arg1, arg2). apply() passes arguments as an array: func.apply(thisArg, [arg1, arg2]). Use call when you know the arguments; use apply when arguments are in an array (or use the spread operator with call in modern JS).
Q74. Explain event bubbling and capturing.
Answer: When an event fires on an element, it goes through three phases: capturing (window → target), target (at the element), bubbling (target → window). By default, event listeners run during the bubbling phase. To listen during capturing, pass { capture: true } to addEventListener. Bubbling allows event delegation (listening on a parent for events from children). You can stop propagation with e.stopPropagation() (stops further bubbling) or e.stopImmediatePropagation() (also stops other listeners on the same element).
Q75. What are the different ways to create an object in JavaScript?
Answer: 1) Object literal: const obj = { key: 'value' } (most common)
2) Constructor function: function Person(name) { this.name = name; } const p = new Person('Alice');
3) Class syntax: class Person { constructor(name) { this.name = name; } }
4) Object.create(): const obj = Object.create(proto)
5) Factory function: function createPerson(name) { return { name }; }
6) Singleton with Object() constructor: const obj = new Object({ key: 'val' })
Q76. What are Set and Map in JavaScript?
Answer: Set is a collection of unique values (no duplicates). Useful for removing duplicates: const unique = [...new Set([1,2,2,3])] // [1,2,3]. Has methods: add, delete, has, size, clear, forEach. Map is a key-value collection where keys can be ANY type (objects, functions) — unlike regular objects where keys must be strings/symbols. Has methods: set, get, delete, has, size, clear, forEach. Use Map when you need non-string keys or frequent additions/deletions.
Q77. What is a polyfill?
Answer: A polyfill is a piece of code that provides modern functionality to older browsers that don't support it natively. For example, if an old browser doesn't support Array.includes, you can add your own implementation. Babel (transpiler) + core-js (polyfill library) handle this automatically in modern build setups. Polyfills are critical for supporting older users while writing modern JavaScript.
Q78. What is the difference between slice() and splice()?
Answer: slice() returns a new array by copying a portion of the array. Does NOT modify the original. arr.slice(start, end) — end is exclusive.
splice() changes the original array by adding, removing, or replacing elements. arr.splice(start, deleteCount, ...itemsToAdd). Returns the removed elements. Example: arr.splice(2, 1) removes 1 element at index 2. arr.splice(1, 0, 'new') inserts 'new' at index 1 without removing anything.
Q79. What is the difference between localStorage and sessionStorage?
Answer: Both store key-value pairs in the browser with ~5-10MB limit. localStorage persists across browser closes and reopens (no expiry). sessionStorage is cleared when the tab closes. Both are synchronous and only store strings. Data is not sent to the server. They are accessed via getItem(), setItem(), removeItem(), clear() methods. Use localStorage for user preferences or cached data; use sessionStorage for temporary state within a session.
Q80. What is the purpose of the module pattern in JavaScript?
Answer: The module pattern provides encapsulation — hiding internal implementation details and exposing only a public API. Before ES modules, this was done using IIFEs (Immediately Invoked Function Expressions) and closures. Modern JavaScript uses ES modules (import/export) which provide built-in module scoping. Benefits: namespacing, preventing global scope pollution, reusability, maintainability. Each module has its own scope — variables are not accessible outside unless explicitly exported.

4. React.js (Q81–Q115)

Q81. What is React? Why use it?
Answer: React is a JavaScript library for building user interfaces, created by Meta (Facebook). It is component-based — you build encapsulated pieces that manage their own state, then compose them into complex UIs. Key benefits: reusable components, virtual DOM for performance, declarative approach (you describe what the UI should look like, not how to change it), huge ecosystem, strong community. React is not a full framework — it's a library focused on the view layer, which makes it flexible to use with other tools.
Q82. Explain the Virtual DOM.
Answer: The Virtual DOM is a lightweight JavaScript representation of the actual DOM. When state changes in a React component: 1) React creates a new virtual DOM tree. 2) It diffs this new tree with the previous one (using a process called "reconciliation"). 3) It calculates the minimal set of changes needed. 4) It applies only those changes to the real DOM (batching updates). This is much faster than directly manipulating the DOM on every change. The Virtual DOM is one of React's key performance advantages.
Q83. What is JSX?
Answer: JSX is a syntax extension for JavaScript that looks like HTML. It's used in React to describe what the UI should look like. JSX is not valid JavaScript — it must be transpiled (by Babel) into React.createElement() calls.
Example: 
const element = <h1 className="title">Hello, {name}!</h1>;
// Transpiles to:
const element = React.createElement('h1', { className: 'title' }, 'Hello, ', name, '!');
JSX makes React code more readable and familiar. In JSX: use className instead of class, use camelCase for attributes (onClick, tabIndex), and wrap multiple elements in a fragment (<></>).
Q84. What are components in React?
Answer: Components are the building blocks of React UIs. Each component is a reusable piece that encapsulates HTML, CSS, and JavaScript logic. Two types: Functional components (JavaScript functions — modern, preferred) and Class components (ES6 classes — older, still used in legacy code). A component takes inputs called "props" and returns React elements describing what should appear on screen. Good components are: focused (single responsibility), reusable, testable, and composable.
Q85. What are props in React?
Answer: Props (short for "properties") are read-only inputs passed to a component. They are like function arguments. Props allow data to flow from parent to child components. Props are immutable — a component should never modify its own props.
Example: 
function UserCard({ name, role, avatar }) {
  return <div><img src={avatar} /><h2>{name}</h2><p>{role}</p></div>;
}
// Usage: <UserCard name="Alice" role="Designer" avatar="/img.png" />
Q86. What is state in React?
Answer: State is data that changes over time within a component. Unlike props (which come from outside), state is internal and managed by the component itself. When state changes, the component re-renders. In functional components, state is managed with the useState hook.
Example: 
const [count, setCount] = useState(0);
// count = current state value
// setCount = function to update it
State updates are asynchronous — don't rely on the updated value immediately after setting. Use the functional updater form for values that depend on previous state: setCount(prev => prev + 1).
Q87. What is the useState hook?
Answer: useState is a React Hook that lets you add state to functional components. It returns an array with two elements: the current state value and a setter function to update it. The initial value can be any type or a function (lazy initialization).
Example with object state: 
const [user, setUser] = useState({ name: '', email: '' });
// Update: setUser(prev => ({ ...prev, name: 'Alice' }));
Always spread existing state when updating objects — React does NOT merge automatically (unlike class component's setState).
Q88. What is the useEffect hook?
Answer: useEffect lets you perform side effects in functional components: fetching data, setting up subscriptions, timers, DOM manipulation, logging. It runs after the component renders (after paint).
Syntax: useEffect(() => { /* effect */ }, [dependencies])
• No dependency array — runs after every render (avoid).
• Empty array [] — runs once on mount (componentDidMount).
• With values [userId] — runs when those values change.
• Return a cleanup function (for subscriptions, timers): return () => clearTimeout(timer).
Q89. What is the difference between useEffect and useLayoutEffect?
Answer: useEffect fires after the browser paints the screen — the user may see a flicker if the effect changes the DOM. useLayoutEffect fires before the browser paints — it runs synchronously after DOM mutations but before the browser renders. Use useLayoutEffect when you need to read layout (getBoundingClientRect) or make visual changes that should be applied before the user sees anything. Use useEffect for most other cases (data fetching, subscriptions, logging) — it doesn't block painting and is better for performance.
Q90. What are React Hooks? Name some built-in hooks.
Answer: Hooks are functions that let you "hook into" React state and lifecycle features from functional components. They were introduced in React 16.8. Rules: only call hooks at the top level (not inside loops/conditions/nested functions), only call hooks from React functions (components or custom hooks). Common built-in hooks: useState, useEffect, useContext, useReducer, useCallback, useMemo, useRef, useLayoutEffect, useImperativeHandle, useDebugValue.
Q91. What is the useContext hook?
Answer: useContext lets you consume a React Context without wrapping components in Consumer components. Context provides a way to pass data through the component tree without passing props manually at every level (prop drilling).
Example: 
const ThemeContext = React.createContext('light');
function App() {
  return <ThemeContext.Provider value="dark"><Toolbar /></ThemeContext.Provider>;
}
function Button() {
  const theme = useContext(ThemeContext);
  return <button className={theme}>Click</button>;
}
Use Context for truly global data (theme, auth, locale). Don't use it for everything — it makes component reuse harder. For complex state, consider useReducer + Context together.
Q92. What is the useReducer hook?
Answer: useReducer is an alternative to useState for complex state logic that involves multiple sub-values or state transitions that depend on previous state. It works like Redux but is built into React.
Example: 
function reducer(state, action) {
  switch (action.type) {
    case 'increment': return { count: state.count + 1 };
    case 'decrement': return { count: state.count - 1 };
    default: return state;
  }
}
const [state, dispatch] = useReducer(reducer, { count: 0 });
// Usage: dispatch({ type: 'increment' })
Use useReducer when: state logic is complex, the next state depends on the previous one, or you're managing a state object with multiple values.
Q93. What is useCallback and useMemo?
Answer: Both are performance optimization hooks. useCallback returns a memoized callback function (caches the function reference) that only changes when dependencies change. useMemo returns a memoized value (caches the result of a computation) that only recomputes when dependencies change.
UseCallback: const handleClick = useCallback(() => doSomething(id), [id]);
UseMemo: const sortedList = useMemo(() => list.sort(), [list]);
Use them when: passing callbacks to optimized child components (React.memo), expensive calculations, preventing unnecessary re-renders. Don't over-optimize — use them only when you have a performance problem.
Q94. What is the useRef hook?
Answer: useRef returns a mutable ref object that persists across renders without causing re-renders when changed. Common uses: 1) Accessing DOM elements directly (focus, measure). 2) Storing mutable values that shouldn't trigger re-render (like interval IDs). 3) Keeping previous values.
Example: 
const inputRef = useRef(null);
const handleClick = () => inputRef.current.focus();
return <input ref={inputRef} />;
Ref values are stored in .current property. Unlike state, changing refs does NOT cause re-render.
Q95. What are controlled vs uncontrolled components?
Answer: In a controlled component, form data is handled by React state — the component controls the input value. Every state change triggers a re-render with the new value. This is the React-recommended approach. In an uncontrolled component, form data is handled by the DOM itself — you use refs to get values when needed (like old-school HTML forms). Controlled gives you more control (validation, instant formatting, conditional disabling); uncontrolled is simpler for basic forms or when integrating with non-React code.
Q96. What is the difference between class components and functional components?
Answer: Class components are ES6 classes that extend React.Component. They have lifecycle methods (componentDidMount, componentDidUpdate, componentWillUnmount) and use this.state / this.setState(). Functional components are plain functions that use Hooks (useState, useEffect). Functional components are simpler, easier to read, less boilerplate, don't have this binding issues, and are the modern standard. React recommends functional components + hooks for all new code.
Q97. What is the React component lifecycle?
Answer: React components go through three phases: Mounting (component is created and inserted into DOM), Updating (props or state change causes re-render), and Unmounting (component is removed from DOM). In functional components with hooks: Mounting = useEffect with [] dependencies; Updating = useEffect with [deps]; Unmounting = cleanup function in useEffect. There's also an Error phase handled by Error Boundaries (componentDidCatch or getDerivedStateFromError).
Q98. What is prop drilling? How do you avoid it?
Answer: Prop drilling is when you pass props through multiple intermediate components that don't need the data — just passing it down to deeper components. It makes code verbose, hard to maintain, and couples components unnecessarily. Solutions: React Context (for global/shared data), State management libraries (Redux, Zustand, Jotai), Component composition (lift the component that needs data up and pass it as children/JSX). Direct prop drilling isn't always bad — for simple depths of 1-2 levels, it's fine. Use context/composition for deeper nesting.
Q99. What is React.memo?
Answer: React.memo is a higher-order component that prevents re-rendering when the props haven't changed. It does a shallow comparison of props — if they are the same, it skips rendering and reuses the last rendered result.
Example: const ExpensiveList = React.memo(({ items }) => { /* render list */ });
Use it for components that: render often with the same props, are expensive to render, or are pure (same props = same output). Don't wrap every component — the comparison itself has a cost.
Q100. What is the difference between React's reconciliation and the diffing algorithm?
Answer: Reconciliation is the overall process React uses to update the DOM efficiently when state changes. The diffing algorithm (also called the "reconciliation algorithm") is the specific method React uses to compare two virtual DOM trees. Key behaviors: 1) If elements have different types, React destroys the old tree and builds a new one. 2) For same-type elements, React updates only the changed attributes. 3) For lists, key props help React identify which items changed. 4) React uses breadth-first search and prioritizes updates for a stable user experience.
Q101. Why is the "key" prop important in lists?
Answer: The key prop helps React identify which items in a list have changed, been added, or removed. A stable, unique key (like a database ID) lets React efficiently update only the changed items instead of re-rendering the entire list. Using array indices as keys is problematic — if the list order changes or items are added/removed, React may reuse wrong component instances leading to bugs. Best keys: unique IDs from data; stable, unique strings. Last resort: index (only for static lists that never change order).
Q102. What is the Context API? When would you use it?
Answer: The Context API provides a way to share values across the entire component tree without prop drilling. It has three parts: createContext (creates the context), Provider (wraps components and provides the value), Consumer (uses the value via useContext hook). Use it for: themes, authentication status, language/locale, UI state (sidebar open/closed). Don't use it for: every piece of state (can make components less reusable), frequently updating data (can cause performance issues — every consumer re-renders on any change).
Q103. What is React Router?
Answer: React Router is a popular library for handling navigation and routing in React apps (client-side routing). It allows you to define routes and render different components based on the URL without page reloads. Key components: BrowserRouter, Routes, Route, Link, NavLink, useParams, useNavigate, useLocation.
Example: 
<BrowserRouter>
  <nav><Link to="/">Home</Link> | <Link to="/about">About</Link></nav>
  <Routes>
    <Route path="/" element={<Home />} />
    <Route path="/about" element={<About />} />
    <Route path="*" element={<NotFound />} />
  </Routes>
</BrowserRouter>
Q104. What is the difference between state and props?
Answer: Props are external inputs passed to a component (like function arguments). They are read-only — the component cannot modify its own props. State is internal data managed by the component that can change over time. Props come from parents; state is local. Changes to props are triggered by parents; changes to state are triggered by the component itself (via setState/setter). Both changes cause re-rendering. Simple rule: if a component manages it, it's state; if it receives it, it's a prop.
Q105. What is Redux? When would you use it?
Answer: Redux is a state management library for JavaScript apps. It uses a single global store and follows three principles: 1) Single source of truth (one store). 2) State is read-only (only changed by dispatching actions). 3) Changes are made by pure reducer functions (no side effects). Flow: component → dispatch(action) → reducer → new state → component re-renders. Use Redux when: you have complex state shared across many components, you need predictable state updates, you want time-travel debugging, or the app has complex async data flows. For simpler apps, React Context + useReducer is often enough.
Q106. What are React Portals?
Answer: Portals let you render a child component at a different place in the DOM hierarchy (outside its parent DOM node) while keeping it in the same React tree. Useful for modals, tooltips, dropdowns, and notifications — these often need to break out of overflow:hidden or z-index contexts.
Example: 
import { createPortal } from 'react-dom';
function Modal({ children }) {
  return createPortal(
    <div className="modal">{children}</div>,
    document.getElementById('modal-root')
  );
}
The modal's events still bubble up in the React tree, not the DOM tree.
Q107. What are Error Boundaries?
Answer: Error Boundaries are React components that catch JavaScript errors anywhere in their child component tree, log those errors, and display a fallback UI instead of crashing the whole app. They only work in class components (using componentDidCatch or getDerivedStateFromError) — there is no hook equivalent yet. Wrap individual features in error boundaries so one broken feature doesn't break the entire page. Error boundaries cannot catch: event handler errors (use try/catch), async code errors, server-side rendering errors.
Q108. What is the difference between shallow rendering and deep rendering in tests?
Answer: Shallow rendering renders only the current component — not its children. Tests are simpler, isolated, and don't depend on child components. Deep rendering (or full rendering) renders the component and all its children — more realistic but slower and more fragile. For unit tests, shallow rendering is preferred (test component in isolation). For integration tests, deep rendering is more useful. React Testing Library encourages "rendering the actual DOM" approach (deep rendering, but testing user behavior rather than implementation details).
Q109. What is the difference between React and React Native?
Answer: React is for building web applications that run in browsers. It uses HTML elements (div, p, span) and renders to the DOM. React Native is for building mobile apps (iOS, Android). It uses native components (View, Text, ScrollView) and renders to native UI components. They share the same React philosophy (components, state, props, hooks, etc.) but have different component libraries. React Native also has its own styling system (similar to CSS but using JavaScript objects with camelCase properties).
Q110. What is Next.js and how does it relate to React?
Answer: Next.js is a React framework that adds features React doesn't have out of the box: server-side rendering (SSR), static site generation (SSG), file-based routing, API routes, image optimization, and more. React handles the UI; Next.js handles the full application structure. Next.js extends React with: pages/router, getServerSideProps, getStaticProps, middleware, layout system. For the TK Opus role, Next.js knowledge is critical since it's explicitly mentioned in the job description.
Q111. How do you optimize React performance?
Answer: • Use React.memo for pure components that re-render too often.
• Use useMemo/useCallback for expensive calculations and stable callbacks.
• Lazy loading components with React.lazy() + Suspense.
• Virtualization for long lists (react-window, react-virtuoso).
• Code splitting with dynamic imports (next/dynamic for Next.js).
• Avoid inline functions/objects in JSX (they create new references each render).
• Use proper keys in lists.
• Debounce/throttle expensive event handlers (search inputs, scroll).
• Profile with React DevTools before optimizing — don't optimize prematurely.
Q112. What is a "lift state up" pattern?
Answer: When multiple sibling components need to share the same state, you lift the state up to their nearest common ancestor. The parent owns the state and passes it down to children via props, along with setter functions so children can update it. This keeps the data flow predictable (unidirectional) and avoids duplicating state in multiple places. This is a core React pattern that appears in many applications.
Q113. How do you handle forms in React?
Answer: Two approaches: Controlled components (state for each form field) — gives full control but more code. Uncontrolled components (useRef to get values) — simpler but less flexibility. For complex forms, use libraries: React Hook Form (performant, less re-renders), Formik (simpler API). Validation libraries: Zod, Yup, or Joi. React Hook Form + Zod is a modern, performant combination used widely in production apps.
Q114. What is the difference between useEffect and componentDidMount?
Answer: componentDidMount is a class component lifecycle method that runs once after the component mounts. useEffect(() => {}, []) with an empty dependency array achieves the same thing. However, useEffect is more flexible — it can run on mount, on updates (with dependencies), and handle cleanup (the return function) all in one place. Also, useEffect runs after the browser paints (slightly different timing than componentDidMount). useLayoutEffect has timing closer to componentDidMount.
Q115. What are custom hooks?
Answer: Custom hooks are JavaScript functions that start with "use" and use built-in hooks to encapsulate reusable logic. They let you extract component logic into reusable functions. A custom hook can manage state, handle side effects, and return values/functions that components can use.
Example: 
function useWindowWidth() {
  const [width, setWidth] = useState(window.innerWidth);
  useEffect(() => {
    const handleResize = () => setWidth(window.innerWidth);
    window.addEventListener('resize', handleResize);
    return () => window.removeEventListener('resize', handleResize);
  }, []);
  return width;
}
Custom hooks are one of the best ways to keep your components clean and share logic.

5. Next.js (Q116–Q140)

Q116. What is Next.js and its key features?
Answer: Next.js is a React framework for production-grade applications. Key features: Server-Side Rendering (SSR) — pages are rendered on the server for better SEO and initial load. Static Site Generation (SSG) — pre-build pages at build time. File-based routing — the file system is the router. API routes — build backend endpoints within the same project. Image optimization — automatic image optimization with next/image. Built-in CSS/SASS support. Middleware — run code before a request completes. Next.js is the most popular React framework and is recommended by the React team.
Q117. What is the difference between CSR, SSR, SSG, and ISR in Next.js?
Answer: • CSR (Client-Side Rendering) — HTML is minimal, JavaScript renders everything in the browser after loading. Slower initial load, harder to SEO.
• SSR (Server-Side Rendering) — HTML is generated on the server for each request. Good for dynamic content that needs SEO. Slower TTFB but better SEO. Uses getServerSideProps.
• SSG (Static Site Generation) — HTML is generated at build time. Fastest possible performance (served from CDN). Best for content that doesn't change often. Uses getStaticProps.
• ISR (Incremental Static Regeneration) — like SSG but can re-build specific pages in the background after a certain time interval. Best of both worlds. Uses revalidate in getStaticProps.
Q118. What is getStaticProps?
Answer: getStaticProps is a Next.js function that fetches data at build time to generate static pages. It runs only on the server (never on the client). The data is used to pre-render the page as static HTML. Used in SSG and ISR patterns. Example: 
export async function getStaticProps() {
  const res = await fetch('https://api.example.com/posts');
  const posts = await res.json();
  return { props: { posts }, revalidate: 60 }; // ISR: rebuild every 60s
}
Q119. What is getServerSideProps?
Answer: getServerSideProps fetches data on every request (at runtime on the server). The page is rendered server-side for each request. Use it when you need fresh data on every load (user-specific dashboards, real-time data, authenticated content). The page will be slower than SSG because it requires a server round-trip. Example: 
export async function getServerSideProps(context) {
  const { params, req, res, query } = context;
  const data = await fetchData(params.id);
  return { props: { data } };
}
Q120. What is getStaticPaths?
Answer: Used with getStaticProps for dynamic routes (e.g., [id].js). It defines which dynamic paths should be pre-rendered at build time. Example: if you have a blog, it lists all blog post slugs. fallback options: false (404 for unknown paths), true (generate on-demand), "blocking" (generate on-demand with SSR-like waiting).
Q121. What are Next.js API routes?
Answer: API routes let you create backend API endpoints within your Next.js app. Files inside pages/api/ (App Router: app/api/) are treated as API routes — they're not pages, they're endpoints. Example: 
// pages/api/hello.js
export default function handler(req, res) {
  res.status(200).json({ message: 'Hello World' });
}
API routes run on the server only. They can handle any HTTP method (GET, POST, PUT, DELETE). Use them for: form submissions, database queries, authentication, webhooks, proxying external APIs.
Q122. What is the Next.js App Router?
Answer: The App Router (introduced in Next.js 13) is a new routing paradigm built on React Server Components, layouts, and streaming. It uses the app/ directory instead of pages/. Key features: nested layouts, server components by default, streaming, built-in loading/error states, and more. Files: page.js (route UI), layout.js (shared layout), loading.js (loading state), error.js (error boundary), not-found.js (404). The App Router is the recommended approach for new projects in Next.js 13.4+.
Q123. What are React Server Components (RSC) in Next.js?
Answer: Server Components are React components that run and render on the server, not the client. They reduce bundle size (server-only code never reaches the client), can directly access databases/backend, and improve initial page load. By default, all components in the App Router are Server Components. Client Components (with "use client" directive) are sent to the browser — used when you need interactivity (state, effects, event handlers). The big insight: most of your app can be server-rendered; only the interactive parts need client code.
Q124. What is next/image and why is it useful?
Answer: next/image is Next.js's built-in Image component that automatically optimizes images. Benefits: automatic responsive sizes (serves appropriate sizes for different screens), WebP/AVIF format conversion (smaller files), lazy loading (only loads when visible), prevents layout shift (reserves space with width/height), blur placeholder while loading. Usage: 
import Image from 'next/image';
<Image src="/hero.jpg" alt="Hero" width={1200} height={600} priority />
Add priority for above-the-fold images (disables lazy loading).
Q125. What is next/link and how is it different from <a>?
Answer: next/link (Link component) handles client-side navigation between pages — no full page reload. It prefetches linked pages (when in viewport) for instant navigation. A regular <a> tag triggers a full page reload. Use Link for internal navigation; use <a> only for external links or downloads.
Example: <Link href="/about">About Us</Link>
Q126. What is the Next.js Layout component?
Answer: In the App Router, layout.js defines a shared layout for a route segment and its children. Layouts persist across navigations (don't re-render) — unlike pages which re-render. This makes them ideal for: navigation bars, sidebars, footers, and other persistent UI. Layouts can be nested (each route segment can have its own layout).
Q127. How does Next.js handle middleware?
Answer: Next.js Middleware runs code before a request is completed. It runs on every request and can: redirect, rewrite, modify headers, add cookies, or block requests. Create a middleware.js (or .ts) file in the root of your project. Common uses: authentication (redirect unauthenticated users), A/B testing, bot detection, internationalization (redirect based on language), geolocation-based redirects.
Q128. What are next/dynamic and dynamic imports?
Answer: next/dynamic is a React.lazy wrapper for loading components on demand (code splitting). This reduces the initial bundle size by splitting rarely-used components (heavy charts, rich text editors, modals) into separate chunks loaded only when needed. Example: 
import dynamic from 'next/dynamic';
const HeavyChart = dynamic(() => import('../components/Chart'), { ssr: false });
The ssr: false option prevents server-side rendering (useful for components that rely on browser APIs).
Q129. How do you add CSS in Next.js?
Answer: Multiple approaches: 1) Global CSS — import in pages/_app.js (traditional). 2) CSS Modules — Component.module.css scoped locally (avoid class name conflicts). 3) Tailwind CSS — built-in support, add PostCSS config. 4) Sass/SCSS — built-in support with .scss files. 5) CSS-in-JS — styled-jsx (built-in), styled-components, Emotion. CSS Modules and Tailwind are the most common choices in the Next.js community.
Q130. What is the next/head component?
Answer: next/head lets you modify the <head> of a page — set title, meta tags, Open Graph tags, etc. Each page can have its own Head component for SEO. Example: 
import Head from 'next/head';
function AboutPage() {
  return <Head>
    <title>About Us | My App</title>
    <meta name="description" content="Learn about our company" />
    <meta property="og:title" content="About Us" />
  </Head>
}
Q131. How do you handle environment variables in Next.js?
Answer: Create .env.local (local dev), .env.production, .env.development files. Prefix with NEXT_PUBLIC_ to expose to the browser. Non-prefixed vars are only available on the server (in getServerSideProps, API routes, getStaticProps). Access: process.env.NEXT_PUBLIC_API_URL. Never put secrets without NEXT_PUBLIC_ prefix in client-side code — they'll be exposed.
Q132. What is the difference between pages/ and app/ directory in Next.js?
Answer: The pages/ directory is the older routing system (Pages Router). Uses files: index.js, [id].js, _app.js, _document.js. Data fetching: getServerSideProps, getStaticProps. The app/ directory is the newer App Router. Uses files: page.js, layout.js, loading.js, error.js. Supports React Server Components, streaming, nested layouts. App Router is the recommended approach for new projects, but Pages Router is still widely maintained and used.
Q133. What is ISR (Incremental Static Regeneration)?
Answer: ISR lets you update static pages after the build without rebuilding the entire site. With ISR, you keep the benefits of static pages (fast CDN delivery) while having fresh content. You set a revalidate time (in seconds). After that time, the first request triggers a background regeneration of the page. The old page is served until the new one is ready. Example: a blog with revalidate: 60 updates at most every 60 seconds. ISR is great for content-heavy sites that don't need real-time updates.
Q134. What are Next.js Font Optimization features?
Answer: Next.js provides built-in font optimization via next/font. It automatically: self-hosts font files (no external requests to Google), eliminates layout shift from font loading, supports variable fonts, and subsets fonts for smaller files. Example: 
import { Inter } from 'next/font/google';
const inter = Inter({ subsets: ['latin'] });
// Usage: <body className={inter.className}>
This is a significant performance improvement over traditional Google Fonts import.
Q135. What is the purpose of the _app.js file?
Answer: In the Pages Router, _app.js is the top-level component that wraps all pages. It's used to: add global CSS, persist layout between page navigations, add global providers (Context, Redux), add Analytics, handle page transitions. Any component prop passed in getInitialProps of _app is available to all pages.
Q136. What is the _document.js file?
Answer: _document.js (Pages Router) customizes the HTML document structure (<html>, <body> tags). It only runs on the server. Use it to: add lang attributes, external fonts, third-party scripts (Google Analytics), or custom CSS-in-JS server rendering. Unlike _app, it does NOT include client-side logic and is not re-rendered on navigation.
Q137. How does Next.js handle redirects and rewrites?
Answer: In next.config.js: redirects — redirect one URL to another (HTTP 301/308/307). User sees the target URL. rewrites — proxy a URL to another URL without changing the address bar. Useful for hiding the real URL structure or proxying to an external API. Example: 
// next.config.js
module.exports = {
  async redirects() { return [{ source: '/old', destination: '/new', permanent: true }]; },
  async rewrites() { return [{ source: '/api/:path*', destination: 'https://api.example.com/:path*' }]; },
};
Q138. What is the Next.js compiler?
Answer: Next.js uses the Rust-based SWC compiler (instead of Babel) for fast compilation and minification. It's much faster than Babel (10-20x). It handles: JavaScript/TypeScript transformation, JSX compilation, code minification, and bundling. You can still use Babel if needed (by adding a .babelrc file), but this disables SWC.
Q139. How do you handle authentication in Next.js?
Answer: Common approaches: 1) NextAuth.js (now Auth.js) — dedicated Next.js auth library supporting OAuth, email, credentials. 2) Clerk, Auth0, Supabase Auth — third-party services. 3) JWT — store token in cookie/localStorage, verify in middleware. 4) Session-based — server-side session stored in database/Redis. Best practice: use NextAuth.js or Clerk — they handle security edge cases you might miss. Use middleware to protect routes and redirect unauthenticated users.
Q140. What is the Edge Runtime in Next.js?
Answer: The Edge Runtime runs code at the CDN edge (closest server to the user) instead of a central server. It's based on Web APIs (not Node.js), so APIs like fs, child_process, or Node.js streams are not available. It runs Middleware and Edge Functions (from Vercel). Benefits: extremely fast response times (geographically close), lower latency, worldwide distribution. Trade-offs: limited APIs, cold starts, memory limits. Use for: authentication checks, geolocation, A/B testing, redirects.

6. UI/UX Design Principles (Q141–Q165)

Q141. What is the difference between UI and UX?
Answer: UI (User Interface) is about the visual appearance — colors, typography, spacing, icons, buttons, layout, visual hierarchy. It's how the product looks. UX (User Experience) is about the overall feel and usability — how easy it is to accomplish tasks, navigation flow, information architecture, user satisfaction. It's how the product works. Good UI without good UX is a beautiful but frustrating product. Good UX without good UI works well but may feel outdated. The best products need both.
Q142. What are the core principles of good UI/UX design?
Answer: • User-centered — design for the user's needs, not your preferences.
• Consistency — same patterns, terminology, and behaviors throughout the app.
• Hierarchy — visually communicate what's most important (size, color, position).
• Simplicity — remove unnecessary elements. Less is more.
• Accessibility — usable by everyone including people with disabilities.
• Feedback — every action should have a visible response (loading, success, error).
• Familiarity — use patterns users already know (shopping cart, hamburger menu).
• Error prevention — prevent mistakes before they happen; when they happen, make recovery easy.
• Affordance — design elements should look like what they do (a button should look clickable).
Q143. What is visual hierarchy?
Answer: Visual hierarchy is the arrangement of elements in a way that implies importance — it guides the user's eye to the most important information first. You create hierarchy through: size (bigger = more important), color (bright/high-contrast = more important), position (top-left = most attention in western reading patterns), spacing (more space around = more important), typography (bold headings, different font sizes), and visual weight (thicker borders, shadows). A clear visual hierarchy helps users scan and understand content quickly.
Q144. What are Fitts's Law and Hick's Law in UX?
Answer: Fitts's Law says the time to reach a target depends on its distance and size. Larger and closer targets are faster to click. Apply this: make important buttons (like "Add to Cart") large and place them where users naturally look. Hick's Law says the time to make a decision increases with the number of choices. More options = slower decisions. Apply this: limit navigation items, break complex forms into steps, simplify menus. Amazon's "Buy Now" button uses Fitts's Law (large, prominent); Google's homepage uses Hick's Law (minimal choices).
Q145. What is responsive design and why is it important?
Answer: Responsive design means a website adapts its layout and content to look good on all screen sizes — from mobile phones to large desktop monitors. It uses flexible grids, images that scale, and CSS media queries. It's important because: over 60% of web traffic comes from mobile devices, Google prioritizes mobile-friendly sites in search results, users expect a consistent experience across devices, and maintaining separate mobile/desktop sites is inefficient. Mobile-first approach (designing for mobile first) is the standard practice.
Q146. What is the difference between wireframes, mockups, and prototypes?
Answer: • Wireframes — low-fidelity, black-and-white layouts showing structure and content placement. No colors, no real content. Purpose: define structure and functionality quickly. Like a blueprint.
• Mockups — medium/high-fidelity, full-color, realistic design. Shows actual colors, typography, images, spacing. Purpose: present the visual design for approval. Looks like the final product but is NOT interactive.
• Prototypes — interactive simulations that let users click through flows. Can be low-fidelity (clickable wireframes) or high-fidelity (near-final design with animations). Purpose: test usability before development. Tools: Figma (all three), Balsamiq (wireframes), Adobe XD, Sketch.
Q147. What is the design thinking process?
Answer: Design thinking is a 5-step human-centered problem-solving process: 1) Empathize — understand the user's needs, pain points, and context through research, interviews, observation. 2) Define — clearly articulate the problem based on what you learned (problem statement). 3) Ideate — brainstorm many solutions, no idea is too crazy. 4) Prototype — create quick, low-cost versions of the best ideas. 5) Test — test prototypes with real users, get feedback, and iterate. This process is non-linear — you often go back to earlier stages based on what you learn. It ensures you solve the RIGHT problem for users, not just build features.
Q148. What are common UX research methods?
Answer: • User interviews — one-on-one conversations to understand behaviors, needs, pain points.
• Surveys — collect quantitative data from many users — satisfaction scores, feature requests.
• Usability testing — watch users try to complete tasks with your product. Identify where they struggle.
• A/B testing — show two versions of a page to different users and measure which performs better.
• Analytics — analyze user behavior data (Google Analytics, Hotjar heatmaps, click tracking).
• Card sorting — users organize content into groups — helps design navigation and IA.
• Tree testing — test if users can find items in your proposed navigation structure.
Choose methods based on what you need to learn and your stage in the design process.
Q149. What is information architecture (IA)?
Answer: Information Architecture is how you organize, structure, and label content in a product to help users find information and complete tasks. Good IA means users can navigate intuitively — they know where to find things without thinking. Key components: navigation systems (menus, breadcrumbs), search systems, categorization/taxonomy, labeling (what you call things), sitemaps. IA is foundational to UX — even a beautiful design fails if users can't find what they need. Best practices: keep navigation shallow (3-4 levels max), use familiar labels, group related content, provide search for large sites.
Q150. What are design patterns in UI?
Answer: Design patterns are proven, reusable solutions to common UI problems. Examples: Navigation patterns — top nav bar, hamburger menu, breadcrumbs, tabs, sidebar. Input patterns — search with autocomplete, dropdown selectors, date pickers, toggle switches. Content patterns — card layouts, accordion, carousel, infinite scroll, pagination. Feedback patterns — toast notifications, loading spinners, progress bars, confirmation dialogs. Using established patterns speeds up design, reduces cognitive load for users (they already know how they work), and improves consistency. Don't reinvent the wheel — use standard patterns unless you have a strong reason to deviate.
Q151. What is accessibility in UI/UX and why is it important?
Answer: Accessibility (a11y) means designing products that can be used by people with disabilities — visual (blindness, low vision, color blindness), hearing (deafness), motor (tremors, paralysis), cognitive (dyslexia, ADHD, memory issues). Importance: 15% of the world's population has some disability, it's legally required in many countries (ADA, WCAG, Section 508), accessible design often improves usability for EVERYONE (captions help in noisy environments, keyboard navigation helps power users), and it expands your audience. Accessible design is good design — it's not an afterthought or a checkbox.
Q152. What are WCAG guidelines?
Answer: WCAG (Web Content Accessibility Guidelines) is the international standard for web accessibility. Four principles: Perceivable — content must be available to senses (alt text, captions, sufficient color contrast). Operable — interface must be usable (keyboard navigation, enough time to read, no seizures from flashing content). Understandable — content and interface must be clear (readable text, predictable behavior, error suggestions). Robust — works with assistive technologies (proper HTML, ARIA labels). Three conformance levels: A (minimum), AA (standard — most common target), AAA (highest — rarely achievable for all content).
Q153. What is color theory in UI design?
Answer: Color theory is the art and science of using colors effectively. Key concepts: Color wheel — primary (red, blue, yellow), secondary (green, orange, purple), tertiary. Color harmony — complementary (opposite on wheel), analogous (adjacent), triadic (120° apart). Color psychology — blue = trust/calm (finance, healthcare), green = nature/health, red = urgency/passion (sales, alerts), yellow = happiness/warning. Practical UI application: use 60-30-10 rule (60% primary neutral, 30% secondary brand color, 10% accent). Ensure sufficient contrast for text (4.5:1 minimum for normal text per WCAG AA). Test for color blindness (don't rely solely on color to convey information).
Q154. What is typography in UI design?
Answer: Typography is the art of arranging text to make it readable, legible, and visually appealing. Key elements: Typeface (font family) — serif (traditional, formal), sans-serif (modern, clean, better for screens), monospace (code). Font size — typically 16px base for body text. Line height — 1.5 for body text. Line length — 45-75 characters per line for comfortable reading. Hierarchy — different sizes/weights for headings vs body. Spacing — letter-spacing, paragraph margins. Best practices: limit to 2-3 font families, establish a type scale (modular scale like 14/16/20/28/38px), ensure sufficient font weight contrast, test readability on different devices.
Q155. What is the 60-30-10 rule in color?
Answer: The 60-30-10 rule is a color balancing guideline for UI design: 60% is your dominant/neutral color (backgrounds, large areas — usually white, gray, or dark depending on theme). 30% is your secondary color (headers, sidebars, sections — often your brand color). 10% is your accent color (CTAs, links, highlights, notifications — contrasting with the other two). This creates a balanced, visually pleasing color scheme where the accent pops without overwhelming. Example: white bg (60%), blue nav/sidebar (30%), orange buttons (10%).
Q156. What is a design system?
Answer: A design system is a complete collection of reusable components, guidelines, and standards that teams use to build products consistently. It includes: design tokens (colors, spacing, typography), UI components (buttons, inputs, cards, modals), pattern library (how components work together), guidelines (accessibility, writing, layout rules), and tooling (Figma component libraries, Storybook for development). Examples: Material Design (Google), Carbon (IBM), Polaris (Shopify). Benefits: consistency across products, faster design and development, easier collaboration between designers and developers, single source of truth.
Q157. What are design tokens?
Answer: Design tokens are the basic design decisions stored as variables — they are the atoms of a design system. Examples: colors (--color-primary: #2563eb), spacing (--spacing-md: 16px), typography (--font-size-body: 16px), shadows, border-radius, animation timing. In code, they become CSS custom properties, Sass variables, or JSON/JS objects. Tokens ensure consistency — changing one token updates the value everywhere. They can be platform-agnostic (used in web, iOS, Android, etc.). Modern tools like Style Dictionary automate generating platform-specific token formats from a single source.
Q158. What is a user persona?
Answer: A user persona is a fictional representation of your ideal user based on research and real data. It includes: demographics (age, occupation, location), goals (what they want to achieve), pain points (what frustrates them), behaviors (how they use products), and a name/photo to make it feel real. Example: "Busy Priya — 32, Marketing Manager, needs to create reports quickly, frustrated with slow tools, uses mobile mostly." Personas help teams: empathize with users, make design decisions with a specific user in mind, avoid designing for yourself, and communicate user needs across the team. Create 3-5 primary personas per project.
Q159. What are the most common UX mistakes?
Answer: 1) Ignoring the user — designing based on assumptions, not real user research.
2) Too many choices — overwhelming users with options (Hick's Law violation).
3) Inconsistent design — different button styles, terminology, or behaviors in different parts of the app.
4) Bad mobile experience — tiny touch targets, non-responsive layouts, zooming required.
5) Ignoring accessibility — low contrast, no alt text, keyboard traps.
6) Too much clutter — information overload, no visual hierarchy.
7) Poor feedback — no loading indicators, no confirmation after actions, unclear error messages.
8) Broken flows — dead ends, confusing navigation, too many steps to complete a task.
9) Slow performance — users leave if a page takes more than 3 seconds to load.
10) Dark patterns — intentionally tricking users (hiding unsubscribe, sneaking items into cart).
Q160. What is user flow and how do you design one?
Answer: A user flow is the path a user takes to complete a task in your product (like signing up, buying a product, or finding information). It maps each step and decision point. To design a user flow: 1) Identify the user's goal (e.g., "order food delivery"). 2) List all steps from start to completion. 3) Map decision points (e.g., "new user? → sign up or guest checkout"). 4) Identify screens/pages needed. 5) Review for friction (too many steps? unnecessary choices?). 6) Simplify. Tools: flowcharts, Figma (with arrows), Miro, Lucidchart. Good flows minimize steps, anticipate user needs, and handle errors gracefully.
Q161. What is the difference between a modal, a drawer, and a popover?
Answer: Modal — a dialog that appears centered on screen, usually with a dimmed overlay, blocking interaction with the rest of the page until dismissed. Use for: critical confirmations, forms that require full attention, terms & conditions. Drawer — a panel that slides in from the side (left, right, bottom). Does not always block the main content. Use for: navigation menus (mobile), filters, secondary content. Popover/tooltip — small floating box anchored to a specific element. Dismissed by clicking outside. Use for: hints, quick actions, additional info without navigation. Rule: use modals sparingly (they interrupt users). Prefer drawers for secondary content and popovers for contextual help.
Q162. How do you design effective forms?
Answer: • Keep it short — ask only for what you truly need. Each extra field reduces completion rate.
• Single column — easier to scan and complete than multi-column layouts.
• Clear labels — visible labels above fields (not placeholder text — that disappears).
• Good defaults — pre-fill when possible (country from IP, date = today).
• Inline validation — show errors immediately (after leaving a field), not after submit.
• Provide feedback — loading state on submit button, success/error message clearly visible.
• Group related fields — personal info, address, payment — use sections/fieldsets.
• Match input to input type — number pad for phone numbers, calendar for dates.
• Forgiving inputs — accept various formats (phone with/without dashes, credit card with/without spaces).
• Accessible — proper labels, error associations, tab order, keyboard navigation.
Q163. What are "dark patterns" in UX?
Answer: Dark patterns are deceptive design patterns that trick users into doing things they didn't intend (buying something, signing up for newsletters, sharing data). Examples: confusing UI to make unsubscribing difficult, hidden costs revealed at checkout, sneaking items into cart, disguised ads (look like content), forced continuity (hard to cancel subscription), confirm shaming ("No thanks, I don't want to save money"). Dark patterns damage trust, violate ethical design principles, and are increasingly regulated (legal consequences in some jurisdictions). As a UI/UX developer, you should advocate against them.
Q164. How do you handle error states in UI?
Answer: Good error handling is crucial for UX. Principles: Prevent errors — use constraints, input masks, clear labels, disabled submit until valid. Clear messages — tell the user WHAT happened and HOW to fix it (not "Error 500" but "Server is busy. Please try again in 30 seconds."). Inline errors — show error next to the relevant field, not at the top of the page. Non-blocking — don't use alert() popups for errors that can be shown inline. Graceful degradation — show a friendly "Something went wrong" fallback UI, not a white screen or code. Retry mechanisms — provide a "Try again" button for transient failures. 404 pages — make them helpful with navigation options, not just "Page Not Found."
Q165. What is gestalt theory in UI design?
Answer: Gestalt principles describe how humans naturally group and interpret visual elements. Key principles for UI: 1) Proximity — elements close together are perceived as related (group related form fields). 2) Similarity — elements that look similar (same color, shape) are perceived as having the same function (all buttons should look similar). 3) Closure — the brain fills in missing parts to form a complete shape (the indentation in a hamburger menu icon). 4) Figure-ground — the eye separates foreground from background (modals with overlays). 5) Common region — elements within a bordered area are perceived as a group (cards, sections). 6) Continuity — the eye follows lines and curves (stepped progress indicators). These principles help you create intuitive, easy-to-scan layouts.

7. Accessibility & Cross-Browser Compatibility (Q166–Q185)

Q166. What is ARIA (Accessible Rich Internet Applications)?
Answer: ARIA is a set of attributes that make web content and applications more accessible to people with disabilities — especially dynamic content and advanced UI controls. Key ARIA attributes: aria-label (provides a label for screen readers), aria-labelledby (references another element as label), aria-describedby (longer description), aria-hidden (hide decorative elements from screen readers), aria-expanded (accordion/menu state), aria-current (current page in navigation), role attributes (role="button", role="navigation", role="alert"). Golden rule: use native HTML elements first (<button> instead of <div role="button">) — they have built-in accessibility. ARIA is for when native elements aren't enough.
Q167. How do you make a website keyboard-accessible?
Answer: All functionality must be usable through the keyboard alone (no mouse required). Key practices: 1) Ensure all interactive elements (<a>, <button>, <input>) can receive focus — use native HTML elements or add tabindex="0". 2) Provide visible focus indicators (the outline around focused elements — never set outline: none without providing an alternative). 3) Logical tab order — tabindex should follow visual order (positive tabindex values are messy, use 0 or -1). 4) Support keyboard shortcuts: Enter/Space to activate, Arrow keys for navigation (menus, tabs, sliders), Escape to close modals/dropdowns. 5) Skip navigation link — "Skip to main content" at the top. 6) No keyboard traps — the user shouldn't get stuck on an element.
Q168. What are skip navigation links?
Answer: A skip navigation link is a hidden link at the very top of a page that jumps to the main content when activated. It's the first focusable element when pressing Tab. It allows keyboard and screen reader users to bypass repetitive navigation links (header, menu). Implementation: 
<a href="#main-content" class="skip-link">Skip to main content</a>
<main id="main-content">...</main>
CSS: position absolute, off-screen, visible on focus. This is a basic accessibility requirement (WCAG 2.4.1).
Q169. How do you test for accessibility?
Answer: Test at multiple levels: 1) Automated tools — axe DevTools (browser extension), Lighthouse (Chrome DevTools), WAVE, Pa11y CI (in CI/CD). Automated tools catch about 30% of issues. 2) Manual keyboard testing — navigate the entire site using only Tab, Enter, Space, Escape, arrows. 3) Screen reader testing — test with NVDA (Windows free), VoiceOver (Mac built-in), JAWS (most popular). 4) Color contrast checkers — WebAIM contrast checker, Stark plugin (Figma). 5) Zoom testing — zoom to 200%, 400% — does content break? 6) User testing — test with people who have disabilities. Remember: automated tools help but cannot replace manual testing — they can't verify if a user flow makes sense.
Q170. What is color contrast and what are the WCAG requirements?
Answer: Color contrast is the difference in luminance between text and its background. WCAG AA (minimum standard): Normal text — 4.5:1 ratio. Large text (18px+ bold or 24px+ regular) — 3:1. UI components (buttons, form inputs) — 3:1. WCAG AAA: Normal text — 7:1. Large text — 4.5:1. Tools: WebAIM Contrast Checker, Stark plugin. Common issues: gray text on white backgrounds, light colored links, placeholder text. Tip: don't rely solely on color to convey information — add icons, patterns, or text labels.
Q171. What are the most common accessibility mistakes you see in web apps?
Answer: 1) Missing alt text on images — screen readers read the filename instead. 2) Poor color contrast — light gray text on white backgrounds. 3) Keyboard traps — elements that can't be focused or escaped. 4) Missing form labels — using placeholder as label (it disappears). 5) Non-semantic HTML — div soup with click handlers instead of <button> elements. 6) No focus indicators — removing outlines without alternatives. 7) Auto-playing audio/video — disorienting for screen reader users. 8) Complex tables without headers — can't be understood by screen readers. 9) Modals that don't trap focus — focus goes behind the modal. 10) CAPTCHAs — difficult for many users; use accessible alternatives (honeypot, rate limiting).
Q172. What is cross-browser compatibility?
Answer: Cross-browser compatibility means making a website work consistently across different browsers (Chrome, Firefox, Safari, Edge) and their different versions. Key challenges: browsers interpret CSS differently, support different JavaScript features, have different rendering engines (Blink for Chrome/Edge, Gecko for Firefox, WebKit for Safari). You handle this by: using standardized code, adding vendor prefixes for experimental CSS (-webkit-, -moz-), using feature detection (Modernizr or similar), testing on multiple browsers, and providing graceful fallbacks for unsupported features. Modern tools like Babel (for JS) and Autoprefixer (for CSS) automate most of this.
Q173. What are CSS vendor prefixes?
Answer: Vendor prefixes are temporary prefixes added to experimental CSS properties before they become standardized. Browsers add their own prefix: -webkit- (Chrome, Safari, newer Edge), -moz- (Firefox), -ms- (old Edge/IE), -o- (old Opera). Example: -webkit-border-radius: 10px; when border-radius was new. Today, build tools like Autoprefixer (used with PostCSS) automatically add the necessary prefixes based on your browser target list. You only need to write standard CSS; Autoprefixer handles the rest. Browsers are better at standard compliance now — vendor prefixes are much less needed than in the past.
Q174. What are feature queries (@supports)?
Answer: Feature queries (@supports) let you apply CSS only if the browser supports a specific property. They are like media queries but for browser features, not screen size. Example: 
@supports (display: grid) {
  .container { display: grid; }
}
@supports not (display: grid) {
  .container { display: flex; } /* fallback */
}
This is the CSS way to implement progressive enhancement — use modern features where available, provide fallbacks for older browsers.
Q175. What is a polyfill and how is it different from transpiling?
Answer: A polyfill is JavaScript code that adds missing functionality to older browsers (e.g., adding Array.includes if the browser doesn't have it). It fills the gap at runtime. Transpiling converts modern code (ES6+) to equivalent older code (ES5) at build time — before the browser sees it. Babel is the most common transpiler. Together: Babel transpiles modern syntax (arrow functions → regular functions); polyfills provide runtime APIs (Promise, Array.from). Core-js is the standard polyfill library, often configured via @babel/preset-env.
Q176. What is graceful degradation vs progressive enhancement?
Answer: Graceful degradation — build the full-featured version first (for modern browsers), then try to make it work in older browsers by stripping back features. The older experience is "degraded." Progressive enhancement — build the core/basic version first (works everywhere), then add enhancements for browsers that support them. The modern experience is "enhanced." Progressive enhancement is generally preferred because: core content works for ALL users, you don't deprioritize older browsers, and it's more resilient (JS fails? core HTML still works).
Q177. How do you test across different browsers?
Answer: 1) Manual testing — install multiple browsers and test key features manually. 2) Browser DevTools — Chrome/Firefox DevTools have device emulation modes. 3) Cross-browser testing services — BrowserStack, Sauce Labs, LambdaTest (test on real devices/browsers in the cloud). 4) Automated visual regression — Percy, Chromatic (screenshot comparison across browsers). 5) Feature detection — check for feature support before using a feature (caniuse.com, @supports). 6) CI/CD integration — automated cross-browser tests in your pipeline. Focus testing on: the most popular browsers among your target audience, the browsers your analytics show, and at least all modern browsers (Chrome, Firefox, Safari, Edge).
Q178. What is the "caniuse" website used for?
Answer: caniuse.com is a reference tool that shows browser support for HTML, CSS, and JavaScript features. You search for a feature (like "CSS Grid" or "fetch API") and it shows a table of which browser versions support it. It also shows global usage statistics. Developers use it to: decide if they can use a modern feature safely, determine if a polyfill is needed, set browser support targets for their project, and check vendor prefix requirements. It's one of the most frequently used tools for cross-browser development.
Q179. What is Normalize.css and why use it?
Answer: Normalize.css is a small CSS file that makes browsers render all elements more consistently — it normalizes default styles across browsers. For example, <h1> has different default sizes in different browsers; Normalize.css makes them consistent. Unlike CSS Resets (which remove all default styling), Normalize.css preserves useful defaults while fixing inconsistencies. Use it as a foundation for any project to eliminate cross-browser surprises. Modern alternatives: Tailwind's base layer includes its own normalization.
Q180. What does the HTML lang attribute do for accessibility?
Answer: The lang attribute on the <html> tag tells screen readers which language the content is in — this affects pronunciation, accent, and voice selection. Example: <html lang="en"> for English, <html lang="hi"> for Hindi. This is critical for accessibility. You can also change language mid-page: <span lang="fr">Bonjour</span>. Without correct lang attributes, screen readers may pronounce words in the wrong language, making content unintelligible.
Q181. Explain aria-live and its use cases.
Answer: aria-live tells screen readers to announce dynamic content changes without the user focusing on that area. Values: off (default, no announcement), polite (announce when idle — for non-urgent updates like new messages count), assertive (announce immediately — for urgent updates like errors/alerts). Use cases: live search results updating, error messages appearing after form validation, chat messages arriving, progress indicators. Also related: aria-atomic (announce the whole region or just changed part).
Q182. How do you make an image accessible?
Answer: Every <img> tag needs an alt attribute. The alt text should describe the image's content and function, not just what it's named. Decorative images (no information value) should have alt="" (empty alt) so screen readers skip them — never omit the alt attribute entirely (screen readers will read the full file path). For complex images (charts, infographics), provide a longer description nearby or with aria-describedby. Icons with meaning need text alternatives: either alt text (for img icons) or aria-label (for SVG icons). Example: <img src="chart.png" alt="Bar chart showing sales increased 40% in Q1 2026">.
Q183. What is a "focus trap" and how do you handle it?
Answer: A focus trap occurs when keyboard focus is locked inside a component (like a modal or drawer) and the user can't tab out of it. This is essential for modals (to keep focus inside) but BAD when unintentional. To implement a focus trap: 1) When modal opens, move focus to the first focusable element inside. 2) Trap Tab/Shift+Tab to cycle through elements inside the modal only. 3) When modal closes, return focus to the element that triggered it. 4) Pressing Escape closes the modal. Many UI libraries (React Aria, Headless UI, Radix) have built-in focus trap components.
Q184. What is the prefers-reduced-motion media query?
Answer: prefers-reduced-motion is a CSS media query that detects if the user has requested reduced motion in their system settings (Windows: Settings → Display → Animations; Mac: Accessibility → Display → Reduce motion). This is important for users with vestibular disorders (motion sensitivity) who can feel dizzy or nauseated from animations. 
@media (prefers-reduced-motion: reduce) {
  *, *::before, *::after { animation-duration: 0.01ms !important; transition-duration: 0.01ms !important; }
}
Always respect this setting — disable or reduce animations, remove parallax effects, and auto-play videos.
Q185. What is the accessibility tree?
Answer: The accessibility tree is a subset of the DOM tree that browsers create for assistive technologies (screen readers). It includes only elements that are semantically meaningful for accessibility — with their roles, states, properties, and text content. Non-semantic elements like decorative images (<img alt="">) and hidden elements (aria-hidden="true") are excluded. Screen readers use this tree to navigate and present content to users. Writing semantic HTML and using proper ARIA attributes ensures the accessibility tree accurately represents your content.

8. Performance Optimization (Q186–Q205)

Q186. What is Core Web Vitals?
Answer: Core Web Vitals are Google's metrics for measuring user experience on the web. Three key metrics: LCP (Largest Contentful Paint) — loading speed of the main content. Should be under 2.5 seconds. FID (First Input Delay) — interactivity (how fast the page responds to user clicks). Should be under 100ms. In 2024, FID was replaced by INP (Interaction to Next Paint). CLS (Cumulative Layout Shift) — visual stability (elements not jumping around). Score should be under 0.1. These metrics affect Google search ranking. As a UI/UX developer, you should monitor and optimize all three.
Q187. How do you improve Largest Contentful Paint (LCP)?
Answer: LCP is the time until the largest element (usually hero image, video, or large text) is visible. To improve: 1) Optimize images — compress, use modern formats (WebP, AVIF), responsive images with srcset. 2) Eliminate render-blocking resources — defer non-critical CSS/JS. 3) Preload key resources — use <link rel="preload"> for hero images. 4) Improve server response time — use CDN, caching, edge rendering. 5) Use SSR/SSG (Next.js) to send fully-rendered HTML. 6) Remove large page elements — reduce unnecessary DOM size. 7) Optimize fonts — use next/font (self-hosted, subset).
Q188. What is Cumulative Layout Shift (CLS) and how to fix it?
Answer: CLS measures unexpected layout shifts during page load. A shift happens when content loads later and pushes existing content down. Common causes: images without dimensions, ads/dynamic content without reserved space, web fonts causing FOIT/FOUT, injected elements (banners, embeds). Fixes: 1) Always set width/height on images and videos. 2) Reserve space for ads and embeds. 3) Use font-display: optional (system font shows until custom font loads). 4) Avoid injecting content above existing content. 5) Use transform animations (don't animate top/left/width/height). 6) In Next.js, use next/image (it reserves space automatically).
Q189. What is code splitting?
Answer: Code splitting is splitting your JavaScript bundle into smaller chunks that load on demand, instead of one giant bundle. Instead of downloading the entire app at once, the browser only loads the code needed for the current page/feature. Techniques: Route-based splitting — each page gets its own chunk (done automatically by Next.js). Component-based splitting — heavy components (charts, editors) load when needed (React.lazy(), next/dynamic). Benefits: faster initial load, less data usage, better performance on slow networks. Measure with Chrome DevTools → Coverage tab to see what code is actually used.
Q190. What is the difference between debouncing and throttling?
Answer: Both limit how often a function runs but work differently: Debouncing — runs the function ONLY after a certain time has passed SINCE the LAST call. If calls keep happening, the timer resets. Use for: search input (wait until user stops typing, then search), window resize (wait until resize finishes). Throttling — runs the function AT MOST once in a given time interval. If calls keep happening, they are ignored until the interval passes. Use for: scroll handlers, infinite scroll, mouse move events, game controls. Example: debounce search (300ms after user stops typing), throttle scroll (run at most every 200ms).
Q191. What are critical CSS and inline critical styles?
Answer: Critical CSS is the minimal CSS needed to style the above-the-fold content (what users see first without scrolling). Inlining means putting this CSS directly into the <head> of the HTML as a <style> tag (instead of an external CSS file that requires a network request). This eliminates render-blocking CSS requests and makes the initial content visible much faster. The non-critical CSS is loaded asynchronously after the page loads. Tools: Critical (by Addy Osmani), PurgeCSS. Next.js does this automatically to some extent. This optimization can significantly improve LCP and First Meaningful Paint.
Q192. How do you optimize images for the web?
Answer: 1) Choose the right format — JPEG for photos, PNG for transparent graphics, WebP/AVIF for everything (smaller files). SVG for icons and logos. 2) Compress — tools like TinyPNG, Squoosh, ImageOptim. 80-90% quality loss is usually invisible. 3) Responsive images — serve different sizes for different screens using srcset and sizes attributes: <img src="small.jpg" srcset="medium.jpg 768w, large.jpg 1200w" sizes="(max-width: 768px) 100vw, 50vw">. 4) Lazy loading — loading="lazy" attribute defers offscreen images. 5) CDN — serve images from CDN or use a service like Cloudinary/Imgix that auto-optimizes. 6) Use next/image in Next.js — it handles all of the above automatically.
Q193. What is lazy loading and how does it work?
Answer: Lazy loading defers loading of resources (images, iframes, components) until they are needed — typically when they come into the viewport. Native HTML lazy loading: <img loading="lazy" src="...">. The browser automatically loads the image when it gets close to the viewport. For components: React.lazy() + Suspense or next/dynamic. Benefits: faster initial page load, less bandwidth usage, fewer server requests. Always add loading="eager" to above-the-fold images (above the fold) and loading="lazy" to below-the-fold images.
Q194. What is a CDN and how does it improve performance?
Answer: CDN (Content Delivery Network) is a network of servers distributed around the world. When a user visits your site, the CDN serves resources from the closest server (geographically), reducing latency. Benefits: faster load times (shorter physical distance), reduced server load, better reliability (if one server fails, another takes over), DDoS protection, edge caching. Examples: Cloudflare, Akamai, AWS CloudFront, Fastly. For Next.js on Vercel, assets are automatically served from the edge CDN. Static files (images, CSS, JS) benefit most from CDNs.
Q195. What is tree shaking?
Answer: Tree shaking is the process of removing dead code (unused exports) from your JavaScript bundle during the build process. Modern bundlers (Webpack, Rollup, Vite) automatically do this when using ES modules (import/export syntax). Example: if you import only useState from React, tree shaking removes unused hooks from the bundle. To enable effective tree shaking: use ES module syntax (not CommonJS), avoid side effects in modules, use production builds, and configure your bundler's sideEffects flag. Tree shaking can significantly reduce bundle size.
Q196. What is the Performance tab in Chrome DevTools?
Answer: The Performance tab records and analyzes runtime performance of your page. It shows: timeline of what's happening (loading, scripting, rendering, painting), FPS (frames per second — low = janky animations), CPU usage, network requests. You can record a session and see exactly which functions take longest, where layout thrashing occurs, and how long the page spends in each phase. Use it to identify: slow JavaScript, forced reflows/recalculations, long tasks blocking the main thread, excessive DOM size, and memory leaks.
Q197. What is the Network tab used for in performance optimization?
Answer: The Network tab shows all network requests made by the page (HTML, CSS, JS, images, fonts, API calls). Key insights: Waterfall — visual timeline of each request. Request count — too many requests hurts performance. File sizes — large files take longer to download. Time to First Byte (TTFB) — server response time. Blocked time — requests waiting for others. Use it to: identify slow resources, find unused CSS/JS, see if resources are cached properly, check for render-blocking resources, verify compression (gzip/Brotli) is working. Throttle network speed (simulate 3G) to test real-world performance.
Q198. What is DOM size and why does it matter?
Answer: DOM size refers to the number of nodes in the page's DOM tree. A large DOM (3000+ nodes) causes: slower rendering, longer style calculations, more memory usage, longer layout/reflow times, and slower querySelector operations. Causes of large DOM: deeply nested component structures, long lists without virtualization, excessive wrapper divs, complex tables. Fixes: reduce nesting (use <Fragment></Fragment> instead of unnecessary divs), virtualize long lists (react-window), avoid deeply nested HTML, limit table rows. Google Lighthouse flags pages with more than 1500 DOM nodes (warning) and 5000 nodes (error).
Q199. What is the difference between HTTP/1.1 and HTTP/2?
Answer: HTTP/2 is faster than HTTP/1.1 because: 1) Multiplexing — multiple requests and responses can be sent over a single connection (vs HTTP/1.1 where each request needed a separate connection). 2) Header compression — HTTP/2 compresses headers (HPACK), reducing overhead. 3) Server push — server can push resources to the client before being asked (deprecated in practice). 4) Binary protocol — more efficient than HTTP/1.1's text-based protocol. With HTTP/2, you no longer need domain sharding (splitting resources across domains) or CSS sprites. Most CDNs and modern servers support HTTP/2.
Q200. What is the difference between <link rel="preload"> and <link rel="prefetch">?
Answer: Both are resource hints but have different priority and timing: Preload — tells the browser "this resource is important; load it NOW." It's used for critical resources (hero images, fonts, above-the-fold CSS). High priority. Example: <link rel="preload" href="font.woff2" as="font" crossorigin>. Prefetch — tells the browser "this resource may be needed later; load it when idle." It's used for resources needed on the NEXT page. Low priority. Example: <link rel="prefetch" href="/next-page.js">. Between them: Preconnect quickly establishes a connection (DNS+TCP+TLS) to an origin before resources are requested: <link rel="preconnect" href="https://api.example.com">.
Q201. What is First Contentful Paint (FCP) vs Time to Interactive (TTI)?
Answer: FCP measures when the first piece of content (text, image, canvas) appears on screen. It's about visual loading — the user starts seeing SOMETHING. Good FCP is under 1.8 seconds. TTI measures when the page becomes fully interactive — JavaScript has loaded, main thread is idle, event handlers are attached. TTI is always after FCP. The gap between FCP and TTI is important: a page might LOAD visually but not be interactive yet (user clicks don't work). Minimize this gap by optimizing JavaScript execution and avoiding long tasks. Core Web Vitals now use INP (Interaction to Next Paint) instead of TTI.
Q202. What are the main causes of slow page load and how do you fix them?
Answer: 1) Unoptimized images — compress, use responsive images, modern formats, CDN. 2) Render-blocking resources — defer non-critical CSS/JS, inline critical CSS. 3) No code splitting — split bundles by routes and components. 4) Large JavaScript bundles — tree-shake, minify, compress (Brotli/gzip). 5) Too many HTTP requests — bundle files, use HTTP/2. 6) Slow server response (TTFB) — use CDN, optimize backend queries, caching. 7) Too many third-party scripts — audit analytics, ads, social widgets; load async. 8) No caching — set proper Cache-Control headers, use service workers. 9) Font loading — self-host, use font-display: swap/optional. 10) Large DOM — virtualize lists, reduce nesting.
Q203. What is a Lighthouse audit?
Answer: Lighthouse is an automated tool (built into Chrome DevTools, also available as CLI and PageSpeed Insights) that audits a webpage across 5 categories: Performance (0-100 score based on Core Web Vitals and secondary metrics), Accessibility (checks for WCAG compliance), Best Practices (secure HTTPS, modern JS, no console errors), SEO (meta tags, crawlability), Progressive Web App (service worker, manifest, offline support). Each audit includes actionable recommendations to fix issues. Run Lighthouse regularly in your development workflow. A score of 90+ is considered good.
Q204. What is a single-page application (SPA) vs multi-page application (MPA)?
Answer: SPA loads a single HTML page and dynamically updates content as users interact — no full page reloads. Built with React, Vue, Angular. Pros: smooth transitions, fast after initial load, rich interactivity. Cons: slower initial load (big JS bundle), SEO challenges (needs SSR), more complex. MPA (traditional) loads a new HTML page from the server for each navigation. Pros: better SEO, faster initial page load, simpler, works without JavaScript. Cons: full page reloads, slower navigation, less app-like feel. Next.js bridges this gap — you can have SPA behavior with MPA benefits (SSR, SSG, client-side navigation).
Q205. What is the rel="noopener" attribute and why use it?
Answer: When you open a link with target="_blank" (opens in new tab), the new page gets access to the original page via window.opener — this is a security risk (tabnabbing — the new page can redirect the original page to a phishing site). rel="noopener" prevents this by setting window.opener to null. Modern browsers treat target="_blank" as automatically having noopener, but it's still best practice to always add it: <a href="..." target="_blank" rel="noopener noreferrer">. The noreferrer also prevents the Referer header from being sent.

9. REST APIs, Git & Modern Workflows (Q206–Q225)

Q206. What is REST API?
Answer: REST (Representational State Transfer) is an architectural style for designing web APIs. It uses HTTP methods for CRUD operations: GET (read), POST (create), PUT (update/replace), PATCH (partial update), DELETE (delete). REST APIs: are stateless (each request contains all info needed), use resource-based URLs (/api/users/123), return JSON data, use status codes for responses (200 OK, 201 Created, 400 Bad Request, 404 Not Found, 500 Server Error). Example: GET /api/products returns a list of products; POST /api/products creates a new product.
Q207. How do you fetch data from an API in React?
Answer: In modern React: 1) Fetch API — built-in browser API: 
const [data, setData] = useState(null);
useEffect(() => { fetch('/api/users').then(r => r.json()).then(setData); }, []);
2) Axios — popular third-party library with cleaner syntax, interceptors, automatic JSON parsing. 3) React Query (TanStack Query) — recommended for real apps. Built-in caching, loading/error states, auto-retry, pagination support. 4) SWR (stale-while-revalidate) — by Vercel. Auto revalidation, caching. 5) Next.js data fetching — getServerSideProps, getStaticProps, server actions. For production apps, use React Query or SWR — they handle edge cases (caching, retry, race conditions) that useEffect+fetch doesn't.
Q208. What are HTTP status codes? Group and common ones.
Answer: HTTP status codes are grouped into 5 classes: 1xx (Informational) — request received, processing. 2xx (Success) — 200 OK (success), 201 Created (POST new resource), 204 No Content (DELETE success). 3xx (Redirection) — 301 Moved Permanently, 302 Found (temporary), 304 Not Modified (cached). 4xx (Client Error) — 400 Bad Request, 401 Unauthorized (not logged in), 403 Forbidden (no permission), 404 Not Found, 409 Conflict (duplicate), 422 Unprocessable Entity (validation error). 5xx (Server Error) — 500 Internal Server Error, 502 Bad Gateway, 503 Service Unavailable. Frontend developers handle 4xx/5xx and show appropriate messages to users.
Q209. What are HTTP methods (verbs) and their use cases?
Answer: GET — retrieve data (read). Safe, idempotent, cacheable. No request body.
POST — create new resource. Not idempotent (creating twice creates two resources). Has request body.
PUT — update/replace entire resource. Idempotent. Sending same data twice has same effect.
PATCH — partial update (only changed fields). Not necessarily idempotent.
DELETE — remove a resource. Idempotent (deleting already deleted resource returns 404).
HEAD — like GET but returns only headers (no body). Check if resource exists, check cache.
OPTIONS — check which HTTP methods are supported (CORS preflight).
In HTML forms, you can only use GET and POST. For PUT/PATCH/DELETE, use JavaScript (fetch/AJAX).
Q210. What is CORS (Cross-Origin Resource Sharing)?
Answer: CORS is a security mechanism that controls which domains can access resources on your server. Browsers block cross-origin requests by default (for security). If your frontend on localhost:3000 calls an API on api.example.com, the browser checks for CORS headers. The server must include: Access-Control-Allow-Origin: https://yourfrontend.com. Other CORS headers: Allow-Methods, Allow-Headers, Allow-Credentials (for cookies). Preflight requests: browsers send an OPTIONS request before actual requests for "non-simple" requests (PUT, DELETE, custom headers). CORS errors are common setup issues — fix them on the server side (backend configures allowed origins).
Q211. What is the difference between authentication and authorization?
Answer: Authentication verifies WHO you are — confirming identity (login with email/password, Google SSO, biometric). Authorization determines WHAT you can access — permissions and roles (admin can delete, user can only view). Authentication comes first; authorization follows. In frontend: authentication is typically handled with JWT tokens, OAuth, or session cookies. Authorization is handled by checking user roles/permissions before showing features. Example: a blog — authentication logs you in; authorization determines if you can edit a post (admin) or only read (regular user). Never rely solely on frontend authorization — backend must also enforce it.
Q212. What are JWT tokens and how do they work?
Answer: JWT (JSON Web Token) is a compact, self-contained way to transmit information between parties as a JSON object. Structure: header.payload.signature — three base64-encoded parts separated by dots. The header specifies the algorithm; the payload contains claims (user ID, role, expiry); the signature verifies the token hasn't been tampered with. Flow: user logs in → server creates JWT → client stores it (localStorage or httpOnly cookie) → client sends it with every API request (Authorization: Bearer <token>) → server verifies and extracts user info. JWTs are stateless (server doesn't store sessions). Security note: store in httpOnly cookies (not localStorage) to prevent XSS attacks.
Q213. What is OAuth 2.0?
Answer: OAuth 2.0 is an authorization framework that lets apps access user data from other services (Google, GitHub, Facebook) without sharing passwords. Flow: 1) App redirects user to the provider (Google). 2) User logs in and grants permission. 3) Provider sends back an authorization code. 4) App exchanges code for an access token. 5) App uses token to access user data. OAuth is used for "Login with Google/Facebook/GitHub." As a UI/UX developer, you integrate OAuth by redirecting users to the provider and handling the callback. NextAuth.js simplifies this in Next.js apps.
Q214. What is Git and why is it important for UI/UX developers?
Answer: Git is a version control system that tracks changes to code over time. It allows multiple developers to work on the same codebase simultaneously, revert to previous versions, and collaborate through branches and pull requests. For UI/UX developers: Git helps track design iterations, collaborate with team members, review code changes before deployment, maintain different feature branches, and roll back if something breaks. Basic workflow: git add → git commit → git push → create Pull Request → code review → merge. Key concepts: repository, commit, branch, merge, rebase, pull request, conflict resolution.
Q215. What is Git branching strategy?
Answer: A branching strategy defines how teams use branches to manage development. Common approaches: Git Flow — main, develop, feature/, release/, hotfix/ branches. Formal but complex. Good for larger teams with releases. GitHub Flow — main branch + feature branches. Simpler: create a branch, commit, open PR, merge to main, deploy. Better for continuous deployment. Trunk-based development — all developers commit to main (or a short-lived branch), very frequent merges. Best for CI/CD. For the TK Opus role: GitHub Flow is the most common in modern startups — simple, works with CI/CD, good for small/medium teams.
Q216. What is a Pull Request (PR) and how do you conduct a good code review?
Answer: A Pull Request is a request to merge changes from one branch into another. It allows team members to review code before it goes to production. Good code review practices: 1) Keep PRs small (under 400 lines) — easier to review thoroughly. 2) Review for: correctness, performance, security, accessibility, consistency with code style, proper error handling. 3) Be constructive — comment on code, not the person. Suggest improvements, don't just critique. 4) Ask questions instead of making demands ("What about this case?" vs "Do it this way"). 5) Check for: missing tests, hardcoded values, console.log statements, accessibility issues, responsive design problems. 6) Approve only when you're confident the code is correct.
Q217. How do you handle merge conflicts?
Answer: A merge conflict occurs when two branches modify the same lines of code. To resolve: 1) Pull the latest changes from the base branch (git pull origin main). 2) Switch to your feature branch (git checkout feature-branch). 3) Merge base branch into yours (git merge main). 4) Git shows conflicted files. Open them and look for conflict markers (<<<<<<<, =======, >>>>>>>). 5) Edit the file to keep the correct version and remove markers. 6) git add the resolved files, then git commit. Use IDE tools (VS Code, WebStorm) for visual merge conflict resolution — they make it much easier.
Q218. What is npm and package.json?
Answer: npm (Node Package Manager) is the default package manager for Node.js. It installs and manages project dependencies (libraries, frameworks, tools). package.json is the project manifest file containing: project metadata (name, version, description), dependencies (packages required for production), devDependencies (packages for development — testing, build tools), scripts (npm run dev, npm run build, npm test), and config (browserslist, engines). Key commands: npm install (install all deps), npm install react (install package), npm run dev (run dev script), npx create-next-app (run package without installing). Alternatives: Yarn, pnpm (faster, more efficient).
Q219. What is the difference between npm and npx?
Answer: npm installs packages and manages dependencies. npx (Node Package eXecute) runs packages without installing them globally. Example: npx create-react-app my-app runs the package directly without having it installed globally. npx is useful for: running one-time commands (scaffolding, linters), trying packages without committing to install, running different versions of the same package, and avoiding global package pollution. npx comes bundled with npm (npm 5.2+).
Q220. What is Postman and when do you use it?
Answer: Postman is an API testing tool that lets developers send HTTP requests (GET, POST, PUT, DELETE) and examine responses without writing code. As a UI/UX developer, you use Postman to: test API endpoints before integrating them into your frontend, understand API response structures and data formats, debug API issues (check headers, status codes, response bodies), test authentication flows, create API documentation collections, and share API configurations with team members. Alternatives: Insomnia (similar, open-source), Thunder Client (VS Code extension).
Q221. What is the difference between development and production builds?
Answer: Development build — optimized for developer experience: full error messages, source maps, hot module replacement, not minimized, slower performance. Production build — optimized for end-user performance: code minified and compressed, dead code eliminated (tree shaking), source maps optional (smaller files), assets hashed for caching, environment variables replaced, no development-only warnings. In Next.js: npm run dev (development), npm run build && npm start (production). Always test the production build before deploying — some bugs only appear in production (different error handling, removed debug logging).
Q222. What is environment variable management?
Answer: Environment variables store configuration that varies across environments (local, staging, production). They keep secrets (API keys, database URLs) out of your codebase. Common files: .env.local (local dev, not committed to git), .env.development, .env.production, .env.example (template with empty values, committed). In React: prefix with REACT_APP_ for client-side vars. In Next.js: prefix with NEXT_PUBLIC_ for browser-accessible vars. Non-prefixed vars are only available on the server. Access: process.env.NEXT_PUBLIC_API_URL. Never commit actual secrets to git — add .env.local to .gitignore.
Q223. What is linting and how does it help?
Answer: Linting automatically analyzes code for potential errors, style issues, and anti-patterns — catching bugs before runtime. ESLint is the standard for JavaScript/React. It checks for: unused variables, missing dependencies in useEffect, improper React hook usage, inconsistent formatting, potential bugs (== vs ===), accessibility issues (jsx-a11y plugin). Benefits: enforces consistent code style across the team, catches bugs early, reduces code review time on style issues, teaches best practices. Use with Prettier (auto-formatter) for maximum benefit. Many projects have lint-staged (runs linter on staged files before commit) in a pre-commit hook.
Q224. What is Prettier and why combine it with ESLint?
Answer: Prettier is an opinionated code formatter that automatically formats your code — handling indentation, quotes, semicolons, trailing commas, line breaks, spacing. It ensures consistent formatting without debates about style (tabs vs spaces, single vs double quotes). It integrates with VS Code (format on save). Combine it with ESLint: ESLint catches LOGICAL issues (bugs, anti-patterns), Prettier handles FORMATTING (how code looks). ESLint: "no-unused-vars": "error". Prettier: printWidth: 80, singleQuote: true, semi: true. Setup: use eslint-config-prettier to disable ESLint rules that conflict with Prettier.
Q225. What is a CI/CD pipeline?
Answer: CI/CD (Continuous Integration / Continuous Deployment) automates building, testing, and deploying code. CI (Continuous Integration) — every code push triggers automated builds and tests. Catches integration issues early. CD (Continuous Deployment) — automatically deploys passed builds to production (or staging). A typical pipeline: push code → run lint → run tests → build app → deploy to staging → run e2e tests → deploy to production. Tools: GitHub Actions, GitLab CI, CircleCI, Vercel (auto-deploy). For UI/UX developers: CI/CD ensures your changes are tested and deployed consistently, catches build errors early, and automates the release process. Never deploy manually from your local machine.

10. Figma, Adobe XD & Design Handoff (Q226–Q240)

Q226. What is Figma and what are its key features for UI/UX developers?
Answer: Figma is a cloud-based design tool used for UI/UX design, prototyping, and collaboration. Key features: Real-time collaboration — multiple people can work on the same file simultaneously. Components and variants — reusable design elements (like React components). Auto Layout — responsive design within Figma (like CSS Flexbox). Prototyping — create interactive flows with transitions. Developer handoff — inspect mode shows CSS values, exports assets. Plugins — extend functionality (icon libraries, accessibility checkers). Design tokens — export colors, spacing, typography as code. Figma is browser-based (no install needed) and supports both designers and developers.
Q227. How do you use Figma for developer handoff?
Answer: Developer handoff is the process of communicating design specs to developers. In Figma: 1) Inspect mode — select any element to see CSS properties (width, height, margin, padding, font size, color, border-radius). 2) Export assets — select elements, choose format (SVG for icons, PNG/WebP for images), and export or copy. 3) Design system / component library — designers create components that developers mirror in code. 4) Annotations — designers add notes for behavior, states, responsive behavior. 5) Handoff plugins — Figma Tokens (export design tokens as JSON), Anima (convert Figma to React code), Zeplin (dedicated handoff tool). Best practice: align design tokens between Figma and code (same color names, spacing scale) so developers can map designs to code easily.
Q228. What is Auto Layout in Figma?
Answer: Auto Layout is Figma's feature for creating responsive, dynamic layouts — similar to CSS Flexbox. It allows frames to automatically adjust based on content. Key properties: Direction — horizontal or vertical (like flex-direction). Spacing between items (gap). Padding around the frame. Alignment — distribute content (center, top, bottom; behaves like justify-content and align-items). Resizing — hug content (grow with content), fill container (stretch to fill), fixed (stay same size). Auto Layout makes designs responsive and reduces manual adjustment when content changes — it's one of Figma's most powerful features.
Q229. What are components and variants in Figma?
Answer: Components in Figma are reusable UI elements — like a button, card, or input field. Changes to the "main component" update all "instances" automatically (similar to React components and props). Variants group component permutations into a single component with different properties — e.g., a Button component with variants: primary/secondary/ghost, and states: default/hover/disabled. Variants simplify component management (no more dozens of separate components for different states). This directly mirrors frontend component systems (like React component variants with props).
Q230. How do you convert a Figma design to code?
Answer: The design-to-code process: 1) Understand the design system — identify colors, typography, spacing, grid system, and components in Figma. 2) Extract design tokens — create CSS variables from Figma's design tokens (colors, fonts, spacing). 3) Build component library — code the reusable components (buttons, inputs, cards) matching Figma's components. 4) Implement layouts — use Flexbox/Grid based on Figma's auto-layout structure. 5) Responsive — implement breakpoints and responsive behavior. Note: Figma is a DESIGN tool, not an output tool — never expect pixel-perfect copies from auto-convert tools. Good developers understand design intent and implement it appropriately in code. Tools like Anima and Figma's Dev Mode can generate starter code, but it needs to be refined for production.
Q231. What is the difference between Figma and Adobe XD?
Answer: Both are UI/UX design tools but with differences: Figma — browser-based (works on any OS), real-time collaboration is core, stronger plugin ecosystem, more popular (wider community), better developer handoff, stronger component system. Adobe XD — desktop app (Mac/Windows), integrated with Adobe Creative Suite (Photoshop, Illustrator), simpler UI for beginners, fewer plugins, older collaboration model (shared links). Adobe has announced XD is in maintenance mode (no new features) — the industry has largely moved to Figma. For the TK Opus role, Figma proficiency is more valuable.
Q232. How do you design for both different screen sizes in Figma?
Answer: Approaches: 1) Multiple frames — create artboards for specific breakpoints (Mobile 375×812, Tablet 768×1024, Desktop 1440×900). Many teams design mobile and desktop and trust auto-layout to handle tablet. 2) Auto Layout + constraints — use auto-layout frames with responsive resizing (fill container, hug content) so elements adapt to different frame sizes. 3) Breakpoint plugin — visualize how your design looks at different widths. 4) Responsive grid — use column grids that match your CSS grid (12 columns, with margins/gutters matching your code). Best practice: design in a mobile-first approach — start with the mobile frame, then expand to desktop.
Q233. What are design tokens and how do you use them between Figma and code?
Answer: Design tokens are the atomic values of a design system — colors, spacing, typography, shadows, radii. In Figma, they live as styles and variables. In code, they become CSS variables or JS constants. To synchronize: use Tokens Studio (Figma Tokens) plugin — it lets you define tokens in Figma and export them as JSON. This JSON can be consumed directly in your code or transformed (using Style Dictionary) to CSS custom properties, Tailwind config, etc. Benefits: single source of truth, designers and developers speak the same language, consistency between design and implementation, can be version-controlled (git).
Q234. How do you use the Inspect panel in Figma?
Answer: The Inspect panel (Developer mode in newer Figma) gives developers the exact CSS values for any selected element: size (width, height), position (x, y), typography (font family, size, weight, line height, letter spacing), colors (hex, RGB), spacing (margin, padding via auto layout), border radius, shadows, opacity. It also shows CSS code snippets, Swift/Android code, and allows exporting assets at different resolutions. To use: select the element in Figma, open the Inspect tab (right panel), view the properties you need. This is the primary way developers extract design specifications from Figma designs.
Q235. What are constraints in Figma (vs Auto Layout)?
Answer: Constraints in Figma define how an element behaves when its parent frame is resized — like CSS positioning (left, right, top, bottom, center, scale). Example: a close button with "top right" constraint stays in the top-right corner when the frame resizes. However, constraints are one-directional (fixed positioning) and don't handle dynamic content well. Auto Layout is more powerful — like CSS Flexbox, it arranges items in a row/column, handles spacing, padding, and wrapping. Auto Layout is now the standard approach; constraints are older and less widely used. Always prefer Auto Layout for responsive designs.
Q236. How do you use a design system in Figma effectively?
Answer: An effective Figma design system includes: 1) Design tokens (colors, spacing, typography as styles). 2) UI component library (reusable components with variants). 3) Pattern library (common page sections — headers, product cards, forms). 4) Icon set (consistent icon library). 5) Documentation (usage guidelines, dos and don'ts). 6) Published as a library — other Figma files can use it (enabling team-wide consistency). As a developer, you should: know where to find the design system, understand how components relate, reference component names that match your code components, report inconsistencies between code and design, and suggest improvements.
Q237. What is Zeplin and how does it help?
Answer: Zeplin is a dedicated design handoff tool that bridges designers and developers. Designers upload Figma/Sketch designs to Zeplin, and developers get: CSS code snippets, measurements, colors, assets, and style guides — all organized. Zeplin adds features Figma's basic inspect doesn't have: comparing different design versions, organizing screens into sections, adding notes/context to specific elements, generating style guides automatically, and integration with tools like Jira and Slack. Some teams use Zeplin alongside Figma; many now use Figma's built-in Dev Mode instead (avoiding the extra cost/tool). For the TK Opus interview, knowing both is good.
Q238. How do you handle responsive images in design handoff?
Answer: In design handoff: designers should provide images at the correct resolution (or in vector format like SVG). They should specify: which images are decorative and don't need meaningful alt text, images that need different crops on mobile vs desktop, and provide hero images at the expected aspect ratio. Developers should: export assets at 1x, 2x (Retina) sizes, use responsive image techniques (srcset, picture element), optimize images for web (compress, WebP format), and implement lazy loading for below-the-fold images. Communication between designer and developer about image behavior at different breakpoints is crucial.
Q239. What is the most common gap between design and development?
Answer: Common gaps: 1) Responsive behavior — designers design at fixed sizes; developers must handle all screen sizes and intermediate states. 2) Dynamic content — designs show ideal content length; real content may be longer/shorter (text overflow, truncation). 3) States not designed — loading states, error states, empty states, edge cases. 4) Animations — designers envision smooth animations; implementing them perfectly takes effort. 5) Accessibility — designs may not consider keyboard navigation, screen readers, or color contrast. 6) Consistency — developers notice inconsistencies in designs more readily (different spacing, font sizes). To bridge gaps: regular designer-developer syncs, shared design system, involving developers early in design reviews, and using real content in mockups.
Q240. How do you collaborate effectively with designers?
Answer: Best practices: 1) Early involvement — join design reviews early, not just after designs are finalized. You can flag technical constraints before the design direction is locked. 2) Speak the same language — learn design terminology (components, variants, auto-layout, constraints). Use the same names for components in code and Figma. 3) Regular check-ins — quick standups or async updates to align on progress. 4) Shared design system — maintain a shared component library with design tokens that both teams reference. 5) Constructive feedback — offer solutions, not just problems ("We can't do that exact animation, but here's an alternative that's 90% similar and performs better"). 6) Involve in QA — let designers review implemented features to catch visual issues. 7) Document decisions — keep records of design decisions and trade-offs.

11. Code Review, Testing & QA (Q241–Q255)

Q241. What are the different types of frontend testing?
Answer: 1) Unit tests — test individual functions, hooks, or components in isolation. Fast, reliable. Tools: Jest, Vitest, React Testing Library. 2) Integration tests — test how multiple components work together (e.g., a form that calls an API). Tools: React Testing Library, Vitest. 3) End-to-end (E2E) tests — simulate real user scenarios in a real browser (click, type, navigate). Most comprehensive but slower and more fragile. Tools: Cypress, Playwright. 4) Visual regression tests — compare screenshots to catch unintended visual changes. Tools: Percy, Chromatic, Playwright. 5) Accessibility tests — automated a11y checks (axe, Lighthouse). The testing pyramid: lots of unit tests (fast), fewer integration tests, even fewer E2E tests (slow). Prioritize tests based on user-critical paths.
Q242. What is React Testing Library?
Answer: React Testing Library (RTL) is a testing utility for React that encourages testing components from the user's perspective — testing behavior, not implementation details. You query and interact with components like a user would: find elements by role, label, text, or placeholder (not by class names or internal state). Example: 
import { render, screen, fireEvent } from '@testing-library/react';
test('button click shows message', () => {
  render();
  fireEvent.click(screen.getByText('Submit'));
  expect(screen.getByText('Submitted!')).toBeInTheDocument();
});
RTL queries by accessibility roles, which also encourages accessibility. Use getByRole, getByLabelText, getByText, findBy (async), queryBy (non-existence). Avoid: container.querySelector (testing internals).
Q243. What is the difference between Jest and Vitest?
Answer: Jest is the traditional JavaScript testing framework (by Meta). Has built-in assertions, mocking, coverage, snapshots. Works with most libraries but can be slower because of transpilation overhead. Vitest is a newer testing framework designed for Vite projects. It's significantly faster (uses esbuild for transforms), has the same API as Jest (easy migration), supports ES modules natively, and has better TypeScript support without extra config. For new projects using Vite/Next.js/Turbopack, Vitest is the recommended choice. For older projects, Jest is still widely used. Both work with React Testing Library.
Q244. What are mocks and stubs in testing?
Answer: Mocks are fake objects/functions that simulate real dependencies. They record how they were called (what arguments, how many times). Example: mocking an API call so the test doesn't actually hit the network. Stubs are also fake objects but provide predefined, canned answers to calls made during the test. Example: a stub that returns a fixed response for a specific input. In Jest: jest.fn() creates a mock function; jest.mock('module') mocks an entire module; jest.spyOn(object, 'method') spies on existing methods. Good mocking practices: mock at the module/API boundary, don't mock what you don't own (unless necessary), avoid over-mocking (test real behavior where possible).
Q245. What is Snapshot testing?
Answer: Snapshot testing captures the rendered output of a component at a point in time and saves it as a reference file. On subsequent runs, the test compares the new output to the saved snapshot — if they differ, the test fails. This catches unintentional UI changes. Example (Jest): 
test('button renders correctly', () => {
  const { container } = render();
  expect(container).toMatchSnapshot();
});
Issues: snapshots can be large, are easy to approve without careful review (developers may just press "update" without checking), and they don't tell you WHY something changed (they just show the diff). Best practices: keep snapshots small (focus on specific elements, not entire pages), review snapshot diffs carefully, use snapshots as a complement to behavior tests, not a replacement. Many teams prefer to use visual regression testing (Percy/Chromatic) instead.
Q246. What is the Testing Trophy concept?
Answer: The Testing Trophy (by Kent C. Dodds) is an alternative to the testing pyramid. It prioritizes: Integration tests (the biggest section) — test how units work together. These give the best confidence-to-effort ratio. Unit tests (smaller section) — test isolated logic (utility functions, complex calculations). Static analysis (TypeScript, ESLint) — catch type errors and style issues at compile time. E2E tests (small slice) — critical user flows. The key insight: integration tests provide the most value for the effort. A component with 3 states can be tested with 1 integration test (testing the user behavior) instead of 3 unit tests (testing each state in isolation). This is the approach React Testing Library encourages.
Q247. What is Playwright?
Answer: Playwright is a modern E2E testing framework by Microsoft. It allows you to: write tests that run in real browsers (Chromium, Firefox, WebKit), automate user interactions (click, type, navigate, drag), take screenshots and record videos, test mobile devices (emulation), intercept network requests, run tests in parallel across browsers. Example: 
import { test, expect } from '@playwright/test';
test('user can log in', async ({ page }) => {
  await page.goto('/login');
  await page.fill('#email', 'user@example.com');
  await page.fill('#password', 'password123');
  await page.click('button[type="submit"]');
  await expect(page).toHaveURL('/dashboard');
});
Playwright is faster and more reliable than Cypress (different architecture — each browser runs in its own process). It's the recommended E2E framework for new projects.
Q248. What is the Cypress testing framework?
Answer: Cypress is an E2E testing framework (and component testing framework) that runs in the browser alongside your application. Key features: real-time reloading (tests re-run as you code), time-travel debugging (go back to see what happened at each step), automatic waiting (no manual sleep/await), screenshots and videos, network stubbing and mocking, and a dashboard for CI results. Cypress architecture: tests run in the same event loop as the app (unlike Playwright where tests run in Node.js). This makes Cypress easier for debugging but limits it to Chromium-based browsers only (for now). Good for: integration tests of critical user flows, component testing (newer feature).
Q249. What is Storybook and how do you use it?
Answer: Storybook is a tool for developing and documenting UI components in isolation. You create "stories" that render each component in different states. Benefits: develop components without needing the full app running, visually test all component states (loading, empty, error, different variants), document components for other developers, run automated visual regression tests (with Chromatic), and test accessibility. Example story: 
// Button.stories.js
export default { title: 'Components/Button', component: Button };
export const Primary = { args: { label: 'Click Me', variant: 'primary' } };
export const Disabled = { args: { label: 'Disabled', disabled: true } };
Storybook integrates with React, Vue, Angular, and many other frameworks. It's a must-have tool for building design systems and component libraries.
Q250. What are some common code review checklist items for UI/UX code?
Answer: When reviewing UI code, check: 1) Functionality — does it work correctly? Test all states and edge cases. 2) Accessibility — proper semantic HTML, ARIA attributes, keyboard navigation, color contrast, focus indicators. 3) Responsive design — does it work on all screen sizes? Check mobile, tablet, desktop. 4) Performance — unnecessary re-renders? Large bundle imports? Unoptimized images? 5) Consistency with design — does it match the Figma design? Check spacing, colors, typography. 6) Code quality — clean, readable code? Proper naming? No console.log? 7) Error handling — what happens when an API fails? Loading states? Empty states? 8) Security — XSS prevention (sanitize user input), proper authentication checks. 9) Browser compatibility — does it work across Chrome, Firefox, Safari, Edge? 10) Tests — are there relevant tests? Do existing tests still pass?
Q251. How do you debug UI issues in the browser?
Answer: 1) Chrome DevTools — most powerful debugging tool:
• Elements tab — inspect and edit HTML/CSS in real-time. Debug layout issues, try CSS changes.
• Console — JavaScript errors, log messages, run ad-hoc JS.
• Sources tab — set breakpoints, step through code, inspect variables.
• Network tab — check API calls, request/response data, timing.
• Performance tab — record and analyze performance bottlenecks.
• Application tab — inspect localStorage, cookies, IndexedDB, service workers.
• Lighthouse tab — run performance/accessibility audits.
2) React DevTools — inspect React component tree, props, state, hooks. 3) Redux DevTools — track state changes, actions, time-travel debug. 4) Console.log() — simple but effective for quick debugging. 5) VS Code debugger — set breakpoints directly in your editor.
Q252. What are the key differences between QA and developer testing?
Answer: Developer testing (unit tests, integration tests) happens during development. It verifies that code works correctly at a technical level — functions return correct values, components render properly, APIs handle data correctly. Developers write and run these tests. QA (Quality Assurance) is a broader process that includes: manual exploratory testing (testers explore the app freely to find unexpected bugs), regression testing (re-testing existing features after changes), usability testing (real users trying the product), acceptance testing (does it meet requirements?), performance testing (load testing, stress testing). QA testers are the user advocates — they test from a user's perspective, not a developer's. In many modern teams, QA is shifting left (earlier in the process) and developers share more responsibility for quality.
Q253. What is manual vs automated testing?
Answer: Manual testing — a human tester uses the app, clicks around, tries different scenarios, and checks for bugs. Pros: catches usability issues, visual inconsistencies, unexpected user behaviors. Cons: slow, expensive, prone to human error, doesn't scale. Automated testing — scripts run tests automatically. Pros: fast, repeatable, runs on every commit, catches regressions, works 24/7. Cons: can't find visual/usability issues easily, needs maintenance, initial setup time. Balance: use automated tests for critical paths and regression prevention; use manual testing for exploratory testing, new features, and UX evaluation. Most teams aim for 70-80% automation coverage with manual testing for edge cases.
Q254. How do you test responsiveness during development?
Answer: 1) Browser DevTools device emulation — simulate phones (iPhone, Pixel), tablets (iPad), desktops. 2) Resize the browser window — drag the window to various widths and watch for breakpoint changes. 3) CSS media query debugging — use DevTools to see which media queries are active. 4) Test on real devices — when possible, test on physical mobile devices (emulators don't simulate touch perfectly). 5) BrowserStack/Sauce Labs — test on real devices in the cloud. 6) Responsive design mode — Firefox has a dedicated Responsive Design Mode (Ctrl+Shift+M). 7) Check common breakpoints — 320px (small phones), 375px (iPhones), 768px (tablets), 1024px (small desktops), 1440px (large desktops). 8) Test content overflow — ensure long text doesn't break the layout (test with dummy content).
Q255. What is TypeScript and why use it in UI development?
Answer: TypeScript is a typed superset of JavaScript that compiles to plain JavaScript. It adds static types: you define what types variables, function parameters, and return values should be. Benefits for UI development: 1) Catch errors early — misnamed props, wrong data types, missing properties — caught at compile time, not runtime. 2) Better IDE support — autocomplete, inline documentation, refactoring tools work much better with types. 3) Self-documenting code — types serve as documentation for how components and functions work. 4) Safer refactoring — change a prop name and TypeScript tells you everywhere it's used. 5) Better team collaboration — types define the contract between components and modules. Modern frameworks (Next.js, React) have first-class TypeScript support. Most production React projects today use TypeScript. Example: interface ButtonProps { label: string; variant: 'primary' | 'secondary'; onClick: () => void; size?: 'sm' | 'md' | 'lg'; }
